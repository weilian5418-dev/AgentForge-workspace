## 1. D11 到底要完成什么

D08 已经回答“做什么、由谁做、用户是否同意”；D09 已经能够准备实例、记录消息并执行原生操作；D10 已经能按停止证明、不可变候选和审核证据决定阶段是否放行。D11 需要回答：

> 此刻该调用哪一个已有服务？如果暂时没有结果，怎样释放进程并持久等待？平台重启后，怎样确认外部 Agent 实际做到了哪里，再决定继续、停止或交接？

例如一个三阶段计划：A 定义接口，B 实现功能，C 写测试。D11 应当自动派发 A，等待有效提交，让 D10 判断 A 是否放行；只有发现真实 ReleaseRecord 后，才派发依赖 A 的 B。B 执行期间平台重启，D11 应先核对原生会话和工作区，再继续观察原任务，不能重新发送 B。

本批终点是“全部必需协作阶段已放行，形成固定版本的集成交接”。整体集成版本、最终检查、用户验收、SSE 属于 D12。D11 不应在最后一个阶段放行后直接将 Run 改为 completed。

### 1.1 固定技术选择

| 事项 | 本批选择 | 原因 |
| --- | --- | --- |
| 平台协作状态图 | LangGraph `StateGraph` | 表达节点、条件转移、checkpoint 与持久中断 |
| 业务状态与操作事实 | 现有 PostgreSQL + SQLAlchemy UnitOfWork | 沿用已经具备的事务、行锁、事件与 outbox |
| checkpoint | `PostgresSaver` 的受租约保护包装器 | 复用现有 PostgreSQL，同时防止失去控制权的 Driver 继续写图状态 |
| 异步传递 | 现有 Procrastinate / outbox | 只传递“有事实变化”“执行此操作”的消息，不再创建另一套业务依赖图 |
| 原生 Agent 执行 | D09 Engine 协调器与 AgentAdapter | 不在 LangGraph 节点内写另一套外部产品工具循环 |
| 等待 | 持久 WaitRecord + interrupt + WakeSignal | 释放图调用与数据库连接，支持重启和补唤醒 |
| 恢复 | 显式 RecoveryCase + 可信观察 + 确认应用 | 不把 checkpoint、租约过期或文本 done 当成原生事实 |
| 并发 | 同 Run 图调用串行；不同合法工作包可通过队列并行 | 先减少平台状态竞争，实际执行并行度由持久领取与准入控制 |

本机已安装的版本是 LangGraph 1.2.20、langgraph-checkpoint-postgres 3.2.0、psycopg 3.3.8、Procrastinate 3.10.0；这些是本次本地读取的结果，不代表网络上的最新版本。按锁文件开发，不必为了 D11 自动升级依赖。

## 3. 如何借鉴“深入 CC”，而不是照搬教学循环

引用来源见文末 S1～S9。这里的 CC 内部文件名来自课程“深入 CC 源码”的分析，本文没有将该分析当成所有 CC 版本的官方稳定接口。下表第三列是针对 AgentForge 的设计选择。

| 课程分析中的机制 | 应理解的代码原则 | AgentForge 写法 |
| --- | --- | --- |
| S1 / s16：ProtocolState、dispatch_message、match_response；深入部分讨论 requestId 与结构化 schema | 请求、响应、执行门控分开；响应必须对应正确请求 | 使用 D09 ProtocolRequest + Pydantic；run 控制和恢复决定同样绑定 request/attempt/session/版本，拒绝只凭自然语言同意 |
| S2 / s17：idle_notification、mailbox、task watcher、tryClaimNextTask；深入部分讨论锁内 busy check 和 claim | 事件负责提醒，领取仍需原子检查依赖和忙碌状态 | 事件 → WakeSignal；Driver 刷新快照 → EligibilityService；Run 行锁内预留 InstanceAttempt，再创建派发消息 |
| S3 / s18：会话级工作区与子 Agent 的 cwdOverridePath，工作区状态独立保存 | 会话存在、工作目录正确、文件快照一致是不同事实 | Recovery 同时核对 NativeSession、GitWorkspace、实际 cwd、候选对象哈希；不因 session 可恢复就声称文件回滚 |
| S4 / s13：后台任务通过通知队列把完成信息送回后续 turn | 长执行不应占住前台协调循环；通知与结果分离 | Worker 执行原生任务，结果入库并写 WakeSignal；Driver 得到通知后查账本；日志正文留在受限存储中 |
| S5 / s11：按 reason/transition 区分恢复路径 | 不同失败原因需要不同动作，恢复次数必须有界 | 实现 RecoveryPolicy，区分纯读取瞬态错误、登录失效、提交结果未知、费用未知和证据失配；不统一 catch 后重发 |

不要直接照搬教学版每秒 `while True` 查文件、内存字典保存 pending_requests 或 JSONL 作为平台权威库。课程展示的是机制；本项目已经有数据库、产品权限边界和阶段门禁，必须把这些机制接到已有约束上。

尤其 s17 教学中的“Agent 自主认领”不代表本平台允许 Agent 改角色分配。平台仍只派发用户确认的工作包和角色。对 AgentForge，“任务可开始”是上游门禁放行，不是收到 idle 或任务文本完成。

## 4. 先讲清楚五种身份、四种版本

### 4.1 五种身份

| 身份 | 用途 | 何时改变 |
| --- | --- | --- |
| run_id | 整次用户任务 | 用户创建新 Run |
| instance_id | 某角色执行实例 | 按领域规则新建或重新绑定实例 |
| native_session_id / session_ref | 平台会话绑定 / 产品原生会话标识 | 新建会话或有证据的交接；二者不能混用 |
| workspace_id | 实际独立文件工作区 | 返工需要新隔离工作区时改变 |
| instance_attempt_id | 某工作包的一次执行 | 第一次派发、获准的返工或替代执行时新建 |

重启 Driver 不应自动新建后面四种身份。

### 4.2 四种版本

- `RunLease.generation`：协调者代次。接管时改变，用于拒绝旧 Driver 写入。
- `Run.active_generation`：整次运行的执行代次。仅在显式作废旧执行并确认安全后改变。
- `Run.status_version`：业务并发版本。用户操作和关键业务状态变更时更新。
- `plan_version / assignment_version / gate_policy_version`：用户确认的计划、分配和门槛版本。

返工通常只建立新 attempt、会话绑定和工作区，不随手提高整个 Run 的 active_generation。若确实提高全局执行代次，必须先核实所有受影响旧执行已停止；否则会把仍运行的其他角色错误地标成失效。

### 4.3 图身份

新增 `GraphBinding` 不可变值对象，字段为 run_id、plan_version、assignment_version、gate_policy_version、execution_generation、graph_version、state_schema_version、checkpoint_epoch。

`thread_id` 使用上述字段规范 JSON 的 SHA-256，例如 `afg:<digest>`；完整可读字段存在 driver_threads。不要把当前 lease token 或 statusVersion 放进 thread_id，否则每次唤醒都变成新图。

stage/workPackage/attempt 是节点操作的绑定，不需要为所有工作包创建独立顶层 thread。初版一个 Run 使用一个串行协调图即可。

初版执行图从用户已确认的完整绑定启动。未确认计划时，Driver 只登记运行级计划确认等待和信号，不建立可以执行开发动作的图；这类 wait 的 thread_id 允许为空，唯一键使用 run_id + wait_key。确认事件到达后再建立正式 thread。图中保留的 plan_confirmation 分支用于检测后续重新规划或分配失效，关闭旧线程并等待新的确认；不能在同一 thread 上修改不可变 GraphBinding 来执行新计划。

## 6. 先把契约与数据库写好

### 6.1 图状态：只保存引用，不保存外部真相

`driver/state.py` 可以这样起笔：

```python
from typing import Literal, TypedDict

class CollaborationState(TypedDict):
    run_id: str
    thread_id: str
    graph_version: str
    state_schema_version: int
    binding_hash: str
    last_observed_sequence: int
    last_snapshot_hash: str | None
    next_action: str
    stage_id: str | None
    operation_ref: str | None
    wait_ref: str | None
    recovery_case_ref: str | None
    handoff_ref: str | None
```

这些字段只说明“图上次观察到了哪里”。`stage_released=True`、`stop_verified=True`、`review_passed=True` 等布尔值不得成为 checkpoint 中的权限事实。每个改变业务的节点都重新查领域账本。

`DriverContext` 则是本次调用的瞬时对象，可以包含 engine、settings、LeaseFence、服务工厂、截止时间；通过 `StateGraph(..., context_schema=DriverContext)` 以及 invoke 的 context 传入。不要将 Session、连接、adapter、签名密钥、lease token 放进 CollaborationState。

### 6.2 新增数据表

建议一次领域迁移实现下列表，另做 graph 包的安装引导；表名可统一加 Row 后缀作为 ORM 类。所有业务表位于 app schema。

| 表 | 关键字段 | 必需约束 |
| --- | --- | --- |
| driver_threads | id、run_id、thread_id、绑定版本、graph_version、state_schema_version、checkpoint_epoch、binding_hash、status、latest_checkpoint_id、last_observed_sequence | thread_id 唯一；同 Run 至多一条 status=active 的线程；完整绑定组合唯一 |
| scheduler_operations | id、run_id、thread_id、kind、operation_key、request_hash、binding_json、status、result_refs、error_code | `(run_id, operation_key)` 唯一；同键异内容冲突 |
| run_waits | id、run_id、thread_id、wait_key、reason、scope_json、predicate_version、after_sequence、status、deadline_at、resolved_by_ref | `(run_id, wait_key)` 唯一；thread_id 可空，仅限执行图建立前的运行级等待；状态 open/resolved/canceled/superseded；索引 run/status/deadline |
| run_wake_signals | id、run_id、source_kind、source_ref、source_sequence、binding_json、priority、status、claim_owner、claim_expires_at、created_at | `(run_id, source_kind, source_ref)` 唯一；索引 status/priority/created_at |
| recovery_cases | id、run_id、request_operation_id、context_hash、context_json、case_version、status、proposed_action、blocker_codes | 同一个未完成控制请求不重复开 case；保存不可变核对上下文 |
| recovery_observations | id、case_id、subject_type、subject_ref、observed_at、support、result_code、evidence_hash、evidence_ref、binding_json | 追加写，不能覆盖旧观察；严格限制 evidence_json 的体积 |
| recovery_decisions | id、case_id、case_version、decision_key、context_hash、decision、actor、reason、evidence_refs、created_at | `(case_id, decision_key)` 唯一；同键异决定冲突；应用过的决定只读 |
| platform_admission | environment_id、mode、version、reason、updated_at | 每个执行环境一条；mode=open/draining/stopped；条件更新 version |

不新建第二张 run lease 表。控制动作的查询状态可以复用现有 `AsyncOperationRow`，operation_type 使用 `run.pause`、`run.resume`、`run.cancel`、`run.recover`；不要把这些完成条件交给原来的模型 operation executor。

`scheduler_operations` 只记录“图已经向哪个领域服务提出哪个意图”，例如关联了哪条 MessageDelivery。原生是否执行仍由 InstanceOperation / DeliveryAttempt 等现有账本拥有，不能在两张表分别声称原生成功。

### 6.3 补齐 InstanceAttempt 的生命周期

扩展现有 `InstanceAttemptRow`，作为协作工作包执行的唯一 attempt。不要再建第三套平行任务尝试表。

建议增加：status、dispatch_delivery_id、scheduler_operation_id、started_at、stop_verified_at、submission_id、superseded_at、error_code。

状态建议：

```text
scheduled → dispatching → running → submitted → awaiting_stop_verification → stopped
                   ↘ unknown              ↘ unknown
scheduled → canceled
running → failed / unknown
stopped → superseded  # 只有明确返工或替代执行才归档
```

`failed` 只表示本次执行失败，并不自动证明子进程停止。如果仍可能写入，状态必须保留 unknown / awaiting_stop_verification，不能释放写入槽。

活跃状态集合包括 scheduled、dispatching、running、submitted、awaiting_stop_verification、unknown。建立部分唯一索引：

```sql
UNIQUE (run_id, work_package_id) WHERE status IN (<active_states>)
UNIQUE (instance_id) WHERE status IN (<active_states>)
```

第一条避免同工作包双执行，第二条避免同实例同时接两份任务。unknown 占槽；不能因超时把它踢出集合。已 stopped 但未获准返工的工作包仍由调度领域规则禁止重新派发。

历史 TaskAttempt 的 Runner/租约用途单独保留，先审计它的调用方。若其与 InstanceAttempt 指向同一协作执行，要保存显式引用关系；不能让两者独立决定一次 Agent 执行的完成状态。

迁移旧记录时不能全部默认 running 或 stopped：有可靠成功停止账本才能回填 stopped；否则归为 unknown 并进入恢复核对。先检测历史重复，再建立唯一索引，不静默删除历史 attempt。

### 6.4 Run 和公开契约的扩展

- Run 增加 `collaboration_state`：idle/running/waiting/ready_for_integration/blocked，以及可空 `collaboration_ready_at`。它是协作进度，不取代原有 Run.status。
- RunActionRequest 增加 `expectedStatusVersion`、`idempotencyKey`。请求体不要允许客户端传“停止已验证”。
- 新增 RunWait、RecoveryReport、RecoveryDecisionRequest、DriverResult 的 Pydantic 契约，继续采用项目 camelCase 别名及 `extra=forbid` 规则。
- 公开响应不包含原生长期凭据、数据库连接串、内部签名密钥或完整 lease token。
- 事件类型和 payload 必须加入 `contracts/events.py` 的显式注册，不能直接写未注册任意字典。

建议事件名：driver.wait_registered、driver.wake_recorded、run.pause_requested、run.paused、run.resume_requested、run.cancel_requested、run.canceled、recovery.started、recovery.observed、recovery.blocked、recovery.applied、run.collaboration_ready。后续按语义精简，避免一条内部心跳写一条业务事件。

## 7. Driver 租约、并发与 checkpoint 要怎样写

这一节要先于 graph.py 实现。只画好图、不做 fencing，会让两个 Driver 都以为自己能继续。

### 7.1 LeaseFence 与锁顺序

新增不可变 `LeaseFence(run_id, owner, token, lease_generation, thread_id, binding_hash)`，只在运行上下文中传递。每次 Driver 片段使用唯一 owner，例如 bootId + workerId + invocationId；续租调用 renew，不重新 acquire。

统一业务锁顺序：

```text
Run → RunLease（需要协调权时）→ Stage（按 ID 排序）→ Instance → Attempt → 子记录
```

用户 API 不持有 Driver 租约，可以只锁 Run 后写控制请求；它不能拿租约替用户授权。异步原生 Worker 根据其领域账本和当前控制状态执行，不需要等待“创建它的那次 Driver 租约”仍活着。

新增两个方法：

```python
def assert_driver_fence(session, fence: LeaseFence) -> None: ...
def run_fenced_transaction(engine, fence: LeaseFence, apply: Callable) -> object: ...
```

`assert_driver_fence` 的顺序：

1. `SELECT Run ... FOR UPDATE`。
2. `SELECT RunLease ... FOR UPDATE`。
3. 获得锁后读取 `clock_timestamp()`，比较 owner/token/generation/expires_at。
4. 复核当前 driver thread 仍 active，计划/分配/门槛/执行代次与 binding 一致。
5. 任何不一致抛 `DriverFenceLost`，本事务回滚。

事务提交前再次检查数据库当前时间与 lease 到期；事务里只做有界读写，不能做网络或文件大遍历。当前 `verify_run_lease` 的时间读取和锁顺序需要调整，不能在锁等待之前取一次 now 后一直用旧时间。

### 7.2 同 Run 图调用串行

使用专用 psycopg 连接获取会话级 advisory lock，键为 `hash('driver-graph:' + run_id)`。使用 try lock，拿不到则返回 busy 并保留待处理信号，不阻塞等待。

这把锁与 D09 的 `native-lane:<instance>` 是两把锁：前者串行化图调用，后者串行化原生发送/停止。Driver 不获得 native lane；它只创建原生操作意图。

该连接使用 AUTOCOMMIT。等待节点持久中断后关闭连接并释放锁，不能让一个等待用户确认的 Run 占着连接几天。

建议初始值：Run lease 60 秒、心跳 10 秒、单次 drive 软上限 15 秒、最多 8 次有业务意义的转移。这是本批起始配置，不是压测结论。超过片段预算时写入可去重的继续信号，然后安全让出；不能因 heartbeat 线程存在而无限运行。`driver_yield` 采用内部立即可满足的等待屏障：wait 和继续信号同事务建立，下一片段识别该屏障后恢复；不能只在内存安排下一次运行，也不能将 LangGraph recursion_limit 异常作为正常让出方式。

### 7.3 PostgresSaver 的 fencing 包装

仅在图外检查租约还不够。图可能在失去租约后才写 checkpoint，所以新增 `FencedPostgresSaver`，通过组合标准 PostgresSaver 实现 BaseCheckpointSaver 公共接口，不修改依赖包源码。

本机版本的关键方法是：

```python
def get_tuple(self, config): ...
def list(self, config, *, filter=None, before=None, limit=None): ...
def put(self, config, checkpoint, metadata, new_versions): ...
def put_writes(self, config, writes, task_id, task_path=''): ...
def get_next_version(self, current, channel): ...
```

具体实现要求：

1. 为一次 drive 创建一条专用 psycopg Connection，AUTOCOMMIT + dict_row，search_path 指向受控 graph schema；不要把 SQLAlchemy 的 Session 当作该连接。
2. graph advisory lock 和底层 PostgresSaver 使用同一连接。连接断开后本片段必须退出，不能静默重连后继续旧 lease。
3. 包装器用自己的 RLock 串行化所有会操作连接的读写调用，避免 checkpoint 后台写入与主线程读共用连接时相互穿插事务。
4. `put` 和 `put_writes` 在这条连接的短事务中，按 Run → RunLease 顺序验证 fence，再调用同连接上的标准 saver，提交前再次核对 expiry。
5. lease 验证和 checkpoint SQL 必须在同一事务、同一连接里。先在 SQLAlchemy 查租约再用另一连接 put 存在竞争窗口，不合格。
6. 未持有效 fence 不提供运行时 delete_thread 或其他破坏性管理入口；读取历史 checkpoint 不赋予继续执行权限。
7. 不启用跨调用常驻 pipeline，不让依赖连接池偷偷替换会话连接。包装器使用的公共方法按当前锁定版本写适配测试。
8. 图调用显式使用 `durability='sync'`。返回或释放租约前确认本次持久写已经完成；仍需业务账本防重，因为 checkpoint 不是外部操作的原子提交。

实现骨架表达的是事务边界：

```python
# 示意：_assert_fence_on_connection 必须使用 self.conn，而非另开 Session。
def put(self, config, checkpoint, metadata, new_versions):
    with self._connection_lock:
        with self.conn.transaction():
            self._assert_fence_on_connection()
            result = self.delegate.put(config, checkpoint, metadata, new_versions)
            self._assert_fence_before_commit()
            return result
```

同样覆盖 put_writes。包装器还必须委托 `get_next_version`、`serde`、`config_specs` 以及锁定版本所需的其他能力，保持底层 PostgresSaver 的版本格式与序列化约定；不能让包装器默认生成整数版本、底层却按字符串版本读取。`list` 若返回惰性迭代器，要在连接锁范围内完成有界读取，不能返回依赖已释放事务的游标。同步初版明确不提供异步图调用，异步接口不能悄悄绕过 fence。补一条 PostgreSQL 测试：让 fence 在写前失效，确认 checkpoint 和 pending writes 均未提交。再测试包装器异常时事务能回滚、连接可以安全关闭。不能只用 mock 测“assert 函数被调用”。

### 7.4 graph schema 安装与权限

`PostgresSaver.setup()` 由一次显式安装/升级命令使用 migrator 执行，不能由每个常驻 Driver 自动建表。使用安装级 advisory lock，按锁定依赖的迁移脚本升级。

SQLAlchemy app metadata 仍不接管 graph 包的内部表。安装后再授予 driver 运行必需的 graph DML；普通 queue worker 不应具有 checkpoint 写权限。现有 grants.sql 的 schema USAGE 和实际表权限需要一起复核，而不是只加一条 USAGE。

默认不允许从不受信来源导入 checkpoint 二进制。图状态只含定义好的基础类型/ID；不要用不受限 pickle 兼容旧状态。版本不兼容时开恢复 case，经过注册迁移器或新线程重建，不在运行时随意 update_state 修改过去。

## 8. 唤醒和等待：最容易写错的地方

LangGraph interrupt 会保存状态并结束本次图调用；恢复使用相同 thread_id 的 Command(resume=...)。官方文档同时说明恢复时节点可能从头执行，因此 interrupt 前的副作用也必须防重。这里把“准备操作”与“真正等待”拆成不同节点。[S6][S7]

### 8.1 业务事实与 WakeSignal 同事务

在 `driver/signals.py` 实现：

```python
def record_wake_signal(
    session,
    *,
    run_id: str,
    source_kind: str,
    source_ref: str,
    binding: dict,
    source_sequence: int | None = None,
) -> WakeSignal: ...
```

调用发生在领域事务里：领域状态更新 → `append_fact` → 写 WakeSignal → 写 outbox `driver.wake`。四者一起提交。outbox payload 的 operationId 使用 signal.id，并带 runId、wakeSignalId、taskVersion。

不必把所有事件都变成唤醒。维护显式 allowlist，例如计划确认、实例创建结果、消息送达结果、有效提交、审核/用户决定、门禁结果、控制动作、恢复观察、授权变化、超时。Driver 自己的心跳、wake_recorded 等不再递归产生唤醒。

既有 `append_fact` 先 flush 再刷新 Run 的保护逻辑必须保留，避免刷新覆盖未提交业务修改。

### 8.2 真实完成通知必须落账

原生 worker 和阶段 worker 结束后，无论成功、明确失败还是 unknown，都写稳定源引用的唤醒，例如：

```text
source_kind=instance_operation, source_ref=<operationId>:<terminalResultVersion>
source_kind=delivery,           source_ref=<deliveryId>:<resultVersion>
source_kind=stage_gate,         source_ref=<gateDecisionId>
source_kind=control,            source_ref=<runControlOperationId>
```

原生执行已经结束但通知丢失怎么办？`sweep.py` 分页扫描未被观察的操作结果与待处理信号，重建同一个去重键，不重做原生执行。

outbox 已确认派发、队列后来丢失时，补扫可以对同 signal 再发 driver.wake。调度提醒本身可重复，不代表外部副作用可重复。

### 8.3 register_wait 要怎样实现

`WaitService.register_or_observe` 的参数包括 fence、wait_key、reason、scope、predicate_version、deadline。

在同一个 Run 行锁事务内：

1. 验证 fence。
2. 读取实际领域条件，以及 Run.last_sequence。
3. 如果条件已经满足，直接返回 satisfied，不创建一个新的等待。
4. 否则插入或复用相同 wait_key 的 open wait，after_sequence 记录本次事实游标。
5. 返回固定 wait_id。

所有会满足条件的领域写入也遵守 Run 行锁及同事务写信号。因此不会在“检查条件还没到”和“登记等待”之间悄悄漏掉事件。即使事件在 wait 提交之后、checkpoint 保存之前到达，持久 WakeSignal 也会在后续 drive 再处理。

等待条件不要存任意 SQL 或可执行函数。存 reason + 受版本化的结构化 scope，由 PredicateRegistry 中明确注册的纯读取函数计算。

首批 reason：

```text
plan_confirmation / workspace_ready / session_ready / task_submission
native_approval / stage_review / user_gate_decision / stop_verification
recovery_evidence / capacity / dependency / driver_yield
```

一个 Run 可以同时有多个未决等待，例如两个角色各有审批。图里 wait_ref 指向本次选择的唤醒屏障；其余 wait 仍在数据库中，事件出现后重新计算快照，不靠一个 last_reason 覆盖所有情况。

### 8.4 真正的 await 节点保持简单

```python
from langgraph.types import interrupt

def await_condition(state, runtime):
    wait = runtime.context.waits.get_bound_wait(state['wait_ref'])
    interrupt({
        'waitId': wait.id,
        'reason': wait.reason,
        'scope': wait.public_scope,
    })
    # resume 中的数据仅表示“需要重查”。下一节点重新读取领域事实。
    return {'wait_ref': None, 'next_action': 'refresh'}
```

不要在这里 create_session、submit_task、签发审批或自动扣费。不要捕获并吞掉 GraphInterrupt。一次 await 节点固定一个 interrupt 调用，避免动态改变多 interrupt 的位置和顺序。

Driver 查询 checkpoint 中的 pending interrupt，并验证其 wait_id 仍属于当前 thread。只有匹配的唤醒、已满足条件或控制动作已取消该 wait，才发送：

```python
Command(resume={'waitId': wait.id, 'wakeSignalId': signal.id})
```

客户端不能直接提供一个 approve=true 作为 Command。用户批准仍走原有授权/计划/门禁 API，先写业务事实，然后才触发 resume。

### 8.5 信号何时算处理完

先持久化本片段 checkpoint/领域修改，再条件更新信号为 completed。崩溃在两者之间会重投，但节点会通过 operation_key 和原账本复用既有结果。

信号绑定旧计划、旧会话、旧代次时标 obsolete 并记录原因，不把它当作当前成功。对于 Run 级 cancel/pause 这种控制命令，按控制操作本身的当前版本核查，不能简单因为它源于旧图就丢掉。

队列重投时可以批量合并“需要重查”的提醒，但不能把未读事件随意标完成。只完成本次实际覆盖的信号/事实游标范围，保留后续新增信号。

## 9. 协作图的节点与路由怎样写

先实现单 Run 串行图。并行的业务包通过不同 outbox 原生操作执行，不通过一堆同时修改 Run 的 LangGraph 节点实现。

### 9.1 建议图结构

```text
START → refresh → decide
                    ├─ 未确认计划 → register_wait → await_condition → refresh
                    ├─ 缺工作区 → ensure_workspaces → refresh
                    ├─ 缺实例 → ensure_instances → refresh
                    ├─ 有合法就绪包 → dispatch_ready → refresh
                    ├─ 有有效提交 → accept_submissions → refresh
                    ├─ 审核/停止/审批中 → register_wait → await_condition → refresh
                    ├─ 有获准返工 → prepare_rework → refresh
                    ├─ pause/cancel 请求 → coordinate_stop → refresh
                    ├─ 有 unknown/恢复请求 → open_recovery → register_wait → await_condition
                    ├─ 全部必需阶段已放行 → prepare_handoff → END
                    └─ 暂无合法动作 → register_wait → await_condition
```

`decide` 是纯函数，不能修改数据库。将其写成：

```python
def choose_next_action(snapshot: CollaborationSnapshot) -> NextAction: ...
```

优先级建议：控制/安全隔离 → 需核对的未知执行 → 已到达提交/审核结果 → 返工准备 → 正常新派发 → 等待 → 集成交接。不要让大量新任务淹没停止请求。

### 9.2 graph.py 的实际写法

```python
builder = StateGraph(CollaborationState, context_schema=DriverContext)
builder.add_node('refresh', refresh_snapshot)
builder.add_node('decide', decide_next_action)
builder.add_node('ensure_workspaces', ensure_workspaces)
# 其余节点按同样方式逐一 add_node。
builder.add_edge(START, 'refresh')
builder.add_edge('refresh', 'decide')
builder.add_conditional_edges('decide', route_action, ACTION_TO_NODE)
builder.add_edge('await_condition', 'refresh')
# 每个短操作节点执行完也回到 refresh。
graph = builder.compile(checkpointer=fenced_saver)
```

`route_action` 只读已经验证的枚举，未知 action 抛显式错误；不要默认路由到 END。每次返回 END 都需要有领域终点事实。

### 9.3 refresh_snapshot

新建 `SnapshotReader.load(run_id, fence)`：在短的 REPEATABLE READ 只读事务中读取 Run、当前 Plan/Assignment、Stage/Release、实例/attempt、未决操作、wait 和控制动作，返回只含必需字段的不可变快照，并计算规范化哈希。

快照用于挑选动作，不是修改权限。后续写入仍在新事务中重新加锁验证。不要先读 Run 再隔几秒读阶段，拼出一个从未真实存在过的状态。

大型消息和产物全文不放在 Snapshot 中。保存 ID、哈希、版本、有限错误摘要；实例正文由既有投递上下文处理。

### 9.4 ensure_workspaces：先给 D07 补协调器

`WorkspacePreparationCoordinator.ensure` 不是在图事务里直接调用 GitService。

第一段短事务：验证计划/授权与 fence；写 scheduler_operation；固定预期 workspace_id、受控目标路径、baseline、角色和 attempt 用途；写 `workspace.prepare` outbox。

第二段 Worker：提交派发意图后，事务外执行 D07 Git/worktree 操作。

第三段短事务：根据实际 worktree 元数据、Git common dir、baseline/head、目录身份、授权根及预期角色保存结果并唤醒。

当前 D07 prepare 方法若内部自行随机创建路径，需要增加可信内部参数或拆低层函数，让协调器能够预先固定 workspace identity。不能 Worker 崩溃后又随机建一份。

发生“Git worktree 已创建，数据库没写回”时，使用固定目标路径和实际 Git 元数据核对；可证明归属才补记既有结果。单个 marker 文件只是线索，不是安全证明；不一致则 RecoveryCase，不删除用户目录来腾位置。

### 9.5 ensure_instances：只写已有 D09 意图

`ensure_instances` 在 fenced UOW 中调用 `ExecutionPreparationService.prepare`，传入当前 planHash、planVersion、assignmentVersion、gatePolicyVersion；幂等键例如：

```text
prepare:<run>:p<plan>:a<assignment>:g<generation>
```

如果已经产生 execution_request 和 instance operation，返回原引用。真正 create_session 仍由 D09 worker 执行。随后等待实际 session ready，不因 prepare 返回 202 就派发工作。

### 9.6 dispatch_ready：必须预留工作槽

新增内部方法 `DispatchService.reserve_and_create_message(session, fence, work_package_id)`，把这些步骤放进同一事务：

1. fence + 当前 Run 控制/admission 校验。
2. 加载当前已确认 PlanSpec；检查工作包与角色、阶段、上游真实 ReleaseRecord。
3. 调用 EligibilityService，核对所需候选输入可以消费。
4. 核对对应实例 active/idle、会话/配置/工作区版本一致。
5. 检查并发上限与当前活跃/unknown attempt。
6. 插入状态 scheduled 的 InstanceAttempt，数据库唯一约束兜底。
7. 创建 scheduler_operation 与 `task.assignment` 消息，关联这个 attempt；写 message.deliver outbox。
8. 保存 result_refs；提交后返回 operation_ref。

当前 `process_delivery` 中“发送前才随机创建 InstanceAttempt”的代码要改成加载这个预留 attempt，并条件更新 scheduled → dispatching。重投只复用它。不要用存在相同正文的 Message 当作已经取得工作槽的证明。

稳定调度键应来自用户批准的执行身份，例如：

```text
assign:<run>:p<plan>:a<assignment>:g<generation>:<stage>:<wp>:r<repairRound>
```

请求哈希额外覆盖目标实例/工作区、objective、上游 release 与候选集合、门槛版本。遇到同键不同正文应冲突，不能换随机 key 绕过。

发送 Worker 不要求创建该意图的 lease 仍有效，因为队列可能在下一次 Driver 才执行；但必须重新核对当前计划、attempt、Run 控制状态、admission、阶段写准入和实例绑定。旧意图失效就拒绝执行。

### 9.7 上游交接不能只传一段摘要

TaskAssignmentPayload 当前只有工作包、objective、stage，D11 需新增可信引用，例如 `inputReleaseRefs`、`inputCandidateRefs`、`contextBundleRef`。字段代表平台解析出的受权输入，不允许调用方声明任意本机路径。

新增 `ReleasedInputResolver.resolve`：按 ReleaseRecord 的允许成员逐一读取候选 ID/哈希/契约版本，检查对象存在、项目归属和消费授权，生成有界上下文包。

不要把“候选已发布”和“D10 已放行”混为一谈。当前 `ArtifactService.can_consume` 主要基于 publication；应接入实际 ReleaseRecord 检查，或提供独立严格的 released-candidate 消费入口，再由派发使用。不能用 publication 存在代替上游门禁。

### 9.8 accept_submissions：补消息到 D10 的桥

`fact.turn_finished`、`idle`、自然语言 done 仅唤醒，不自动构造 StageSubmission。

实现 `SubmissionBridge.accept(message_or_receipt_ref)`：只接受已经验签、类型正确、绑定当前 instance/session/attempt/generation/stage 的结构化提交。提交内容必须能转换为 StageSubmissionRequest，并核对工作包、产物契约和实际尝试。

桥接调用 `StageService.submit`，幂等键使用原始受信消息/receipt 的稳定 ID。阶段停止、冻结、验证和审核继续通过 D10 stage.stop_verify 链路执行。若产品仅能输出自然语言，进入明确的人工辅助提交流程，不假装已经收到结构化成功。

### 9.9 prepare_rework

当 D10 产生 ReworkOrder：先请求并核对旧执行停止、关闭旧会话绑定；按 D07 准备新隔离工作区；再调用 `StageService.accept_rework(order_id, workspace_id=...)`。

补充同步更新：旧 attempt 只有确认无写入后才能标 superseded；新 attempt 通过 reserve_and_create_message 建立。按 D10 选择的 target_role 和工作包定向派发，不能重跑整个图或让其他已放行分支回到开发态。

### 9.10 prepare_handoff

核对全部必需包与阶段 ReleaseRecord 已满足，包含 dependency_branch 下跨分支的未决依赖。用固定候选、release ID、计划/分配/契约/环境版本生成 `IntegrationHandoff`，保存为一种 scheduler_operation 的不可变结果及哈希。

然后设置 `Run.collaboration_state=ready_for_integration`，写 `run.collaboration_ready` 事件，图安全结束。Run.status 不改 completed，也不提前改 awaiting_acceptance。

D12 以后消费这个交接记录。D11 不应先写一个无人处理的 integration.requested outbox；如要启用该类型，必须同时实现已注册处理器及失败状态，不能复现 D09 曾经的悬空消息链。

## 10. drive_once 的完整执行顺序

建议入口：

```python
def drive_once(
    settings: Settings,
    *,
    run_id: str,
    wake_signal_id: str | None,
    owner: str,
) -> DriverResult: ...
```

不要把这个入口实现成常驻大循环。一次调用只协调一个有界片段：

1. 以受信 driver 角色打开图连接，try 获取 run 的 graph advisory lock。
2. 短事务取得 RunLease；锁内查看控制状态，确认/选择当前 GraphBinding；按唯一键建立或复用 driver_thread。
3. 领取该 Run 一小批 pending signal；记录 claim。源消息只作为查询线索，不作为业务事实。
4. 启动有界心跳；构造 FencedPostgresSaver、DriverContext 和编译后的图。
5. 读取该 thread checkpoint；不存在时从业务事实初始化。
6. 若存在 pending interrupt，用 WaitService 重新核对相关 wait；满足/取消后才传 Command(resume=...)，否则保留等待并结束片段。
7. 若 checkpoint 含失败后可恢复的纯协调节点，从原 thread 继续；遇到 binding/图状态版本不兼容先开恢复 case，不能直接执行。
8. 图以 sync durability 运行；节点只通过 fenced transaction 写领域意图。
9. 返回 interrupted / yielded / ready_for_integration / blocked 等有解释的 DriverResult。
10. 已持久覆盖的 signal 条件标 completed；未覆盖的继续 pending。保存 thread 的最新 checkpoint 引用和观察游标。
11. 停止心跳，仅在仍匹配 token 时释放自己的 lease；解锁并关闭图连接。

Graph checkpoint 与 app 领域事务通常不是一个原子事务，因此必须允许“业务已经提交，checkpoint 尚未保存”的崩溃窗口。D11 的正确性来自领域幂等和恢复对账，不来自假设这两次提交永远同时成功。[S6][S8]

### 10.1 复用领域操作的通用模板

`SchedulerOperationService.ensure` 可以统一这个模式：

```python
def ensure(session, *, fence, operation_key, request_body, apply):
    assert_driver_fence(session, fence)
    digest = canonical_request_hash(request_body)
    existing = repository.find_operation(operation_key)
    if existing is not None:
        assert_same_hash(existing, digest)
        return existing.result_refs
    operation = repository.add_operation(operation_key, digest)
    result_refs = apply(session)  # 只能做短事务内领域意图，不调用原生 API
    operation.result_refs = result_refs
    operation.status = 'waiting'  # 等待子操作事实；不声称原生成功
    return result_refs
```

唯一约束是并发兜底，不是把 IntegrityError 全部当成功。冲突后回读原记录并比较 hash；若本事务已经处于失败态，需要 savepoint 或回滚后新事务，不能继续拿失效 Session 查询。

不是所有 replay 都应该返回“成功”。原操作 unknown 时返回相同 operation_ref 和 needs_reconciliation，不能通过换 key 再创建一条。

### 10.2 未知异常的分类

- `DriverFenceLost`：立即停止图写入；不取消远端任务；信号留待下一协调者。
- 纯数据库事务失败且未调用外部：回滚，可由队列按策略有限重试。
- 已写 outbox：确认领域记录后复用，不能另建副作用。
- 原生调用已开始但结果不明：由既有账本标 unknown，进入恢复，不按图 retry 重发。
- 图版本不兼容：blocked，要求显式迁移/重建决定。
- 代码缺陷或不支持的节点：保留错误引用、停止自动推进，不用 END 吞掉异常。

LangGraph task 可以帮助复用已完成任务结果，但不能消灭外部动作完成、结果记录前的崩溃窗口。本项目第一版把原生 I/O 留在已有持久 Worker，节点无需再用一层 task 包裹同一个原生调用。[S6][S8]

## 11. 恢复服务：分三段写，不要“一键继续”

### 11.1 RecoveryCase 固定核对上下文

`RecoveryService.open_case(run_id, reason, request_operation_id)` 在短事务中：

1. 锁 Run，读取当前计划/分配/门槛/执行代次。
2. 收集实例、NativeSession、当前 attempt、工作区和未决原生操作。
3. 固定 stage/candidate/contract/environment 哈希，保存未决审批和预算 reservation 引用。
4. 计算 context_hash，保存 context_json 与 case_version。
5. 写 recovery.inspect outbox；不在事务内调用 adapter.inspect_execution。

所有观察属于这个上下文。若核对期间用户换计划/撤销授权，不能把原来的“可继续”直接应用到新上下文。

### 11.2 RecoveryProbeCoordinator 在事务外采集观察

新增方法：

```python
def probe_case(engine, settings, case_id: str) -> RecoveryReport: ...
def inspect_instance(adapter, context: TrustedInspectionContext) -> NativeObservation: ...
def inspect_workspace(context: TrustedInspectionContext) -> WorkspaceObservation: ...
def inspect_pending_operations(context: TrustedInspectionContext) -> list[OperationObservation]: ...
```

执行结构：短事务领取并提交 probe 意图 → 事务外受信 Host/Adapter/Git/对象存储检查 → 短事务保存不可变观察并唤醒。

NativeObservation 至少记录 sessionRef、nativeSessionId、instanceId、attemptId、generation、workspaceId、actualCwd、running、childrenRunning、writesQuiesced、observedAt、support、evidenceRef。缺任何必要安全事实都表示 unknown，不能用默认 False 填充。

现有 Adapter.inspect_execution 返回宽字典；D11 应增加 Pydantic 归一化层和版本号。原生实际检查必须由产品/Host 实现，不能仅把待查参数原样回显当作观察证据。

同样，原生事件入口补齐 plan/assignment/generation/attempt/workspace 的精确比较；已绑定字段省略也拒绝。旧消息/报告先保存为历史观察或 stale receipt，不改新执行状态。

### 11.3 每次至少核对六组事实

| 维度 | 读取和比对 | 不符合时 |
| --- | --- | --- |
| 业务授权 | 当前计划确认、角色分配、配置与能力证据、目录 grant、模型/动作授权 | 阻塞新派发；必要安全停止走原会话历史绑定 |
| 原生执行 | 产品会话真实存在、会话归属、子执行、实际 cwd、可写状态、所需 resume 能力 | unknown 或定向停止/人工核对 |
| 文件工作区 | workspace 身份、真实路径、目录授权、Git common dir/head、基线/角色/attempt 对应 | 冲突报告，不自动 reset/checkout 清除用户改动 |
| 候选与阶段 | 对象哈希、CandidateSet 指纹、D10 审核版本、ReleaseRecord | 旧证据失效，回 D10 或开返工 |
| 原生副作用 | create/send/stop/approval 等 prepared/unknown 是否实际发生 | 可查询则对账；不能查则保留未知，不重发 |
| 模型费用 | call/attempt/reservation/usage/settlement 是否一致 | 保留原预留与未知费用；不得因超时自动退款后再发一次 |

读取 Host 断连、登录过期、返回 unsupported 都不是“原会话不存在”。只有对该绑定的明确可验证观察，才能作为 absent/stopped 证据。

### 11.4 RecoveryPolicy 是纯函数

```python
def decide_recovery(
    context: RecoveryContext,
    observations: tuple[RecoveryObservation, ...],
) -> RecoveryRecommendation: ...
```

返回 action、reason_codes、required_evidence、requires_user_decision；它不直接修改 Run，也不调用原生。

| 发现的事实 | 推荐动作 | 实际含义 |
| --- | --- | --- |
| 原会话与当前绑定一致，任务仍在跑 | observe_existing | 继续收事件/检查；不再次 submit_task |
| 已有正式提交且可信停止已确认 | continue_stage_processing | 使用原 attempt 进入 D10，不创建替代尝试 |
| 旧执行已停止，会话支持经实测的原生续接 | resume_existing | 在原会话续接；复核权限和当前允许动作 |
| 原会话不能恢复，但旧执行已核实停止 | handoff_new_session | 新会话、新绑定/工作区、带出处的交接；公开为“新会话交接” |
| 原生发送成功与否无法判断 | await_reconciliation | 保留 operation unknown，禁止重复发送 |
| 工作区或候选哈希变了 | block_or_rework | 固定冲突证据，走 D10 定向返工/计划修订 |
| 登录/授权失效 | wait_authorization | 等待重新验证；不沿用旧 approvals 扩权 |
| 存在无法核对的活跃旧子进程 | await_stop_verification | 不能派发会写同一范围的新尝试 |
| 平台图状态落后于业务账本 | rebuild_projection | 从可信领域事实重建协调状态，保留旧 checkpoint 审计 |

图状态较新也不能覆盖外部事实。若 checkpoint 说调用成功但无操作账本/原生证据，应开缺证据问题，不能按 checkpoint 自动补成功。

### 11.5 apply_decision 必须再次条件检查

```python
def apply_decision(
    session,
    *,
    case_id: str,
    expected_case_version: int,
    expected_context_hash: str,
    expected_status_version: int,
    decision_key: str,
    decision: RecoveryDecision,
    actor: str,
) -> OperationAccepted: ...
```

锁 Run 与 case，复核当前业务版本和必要观察是否仍新鲜；核对当前 case 没被另一个决定应用；写决策记录、操作意图、事件和 outbox 后一起提交。

自动应用只限于不扩大权限、绑定不变且证据充分的继续观察/复用既有结果。改变会话、工作区、权限范围或承认无法恢复的结果，需要相应用户决定，不能把用户点击 resume 解释成任意新建产品会话授权。

人工决定也不能创造不存在的安全证据。“我承担风险”只记录为意见，不把 unknown 改成 stopped，不释放仍可能写入的工作槽。

## 12. 原生 resume 和新会话 handoff 要明确分开

当前代码的 `resume_or_handoff` 协议已经声明，但通用适配器明确 unsupported；instances.worker 的实际分支也没有完成一个经验证的 resume 执行链。D11 必须正面补这一点，而不是仅新增 run.resume 路由。

### 12.1 先定义结果，再接适配器

在 contracts/recovery.py 定义带 discriminator 的结果：

```text
resumed_existing：同一个 sessionRef/nativeSessionId，附原生续接证据
handoff_required：原生续接不可行，只提出下一步，不自动新建会话
unsupported：明确不支持
unknown：可能已经发生原生动作，必须核对
failed：有证据的明确失败
```

可以保留已有方法名作为兼容外观，但受信 ResumeCoordinator 必须强制该语义。禁止 adapter 在一个含糊 resume_or_handoff 调用里悄悄新建会话，再返回 resumed。

实例 resume 也使用三段式持久协调：提交原生操作意图 → 事务外原生续接 → 提交回执。结果未知时不再调用同一次续接。

### 12.2 handoff 包应该有什么

`HandoffManifest` 至少包含：

- 原 run / plan / assignment / stage / workPackage / attempt。
- 原实例、会话、工作区与可信停止/关闭证明。
- 原计划目标、当前允许的任务、已经完成和明确未完成的部分。
- 固定候选/已放行输入的 ID、哈希和契约版本。
- 未决审核、阻塞原因、明确的不确定副作用/费用。
- 需要重新获得的权限；敏感数据不能因写入摘要自动取得外发授权。
- handoffHash、生成策略版本、来源证据引用。

初版优先规则生成交接包。若以后用模型压缩内容，必须单独走 D01 的模型授权和预算，且模型摘要不能改变原始证据的可信级别。

### 12.3 交接操作顺序

1. 证明原执行及可写子进程已停止。
2. 关闭/失效旧 NativeSession 绑定，保留原记录。
3. 按当前批准范围准备新隔离工作区；不是恢复旧文件内容。
4. 当前角色/产品/配置有变则先重新分配并确认。
5. 新会话创建单独记账，不能复用旧 create operation。
6. 新 attempt 绑定 handoffManifest，再发允许的剩余任务。
7. 旧会话事件只进历史，不覆盖新会话。

不能在“原会话暂时联系不上”时跳到第 3 步。只有旧执行安全边界成立，才能建立可能写入的新尝试。

## 13. pause、cancel、resume、drain 具体怎么实现

### 13.1 pause：先阻止新工作，再核对已有工作

API 的同步部分只做：锁 Run → expectedStatusVersion/idempotency 校验 → 状态 pause_requested → 创建 AsyncOperationRow → 写事件和 WakeSignal。

这一事务提交后，所有产生新开发副作用的领取入口都必须拒绝：新工作区/实例创建、task.assignment、需要开发写入的 Runner、原生续接等。允许已有执行的结果落账、受信查询、停止、关闭及必要审核证据保存；不能为了暂停让安全收尾也无法执行。

Driver 的 coordinate_stop 给当前可写执行建立稳定 request_stop 操作，并等待 D09 真实 stopProof。全部受影响执行写入静止且无可开始的新派发后，才转 paused。

pending create/send 如果还没有可能调用原生，可以条件撤销；已经进入 unknown 的不能改 canceled 来掩盖。pause 不能因等待 30 秒就自动成功，也不把所有 stage.write_access_closed 当永久关闭；暂停限制由 Run 控制状态拥有。

### 13.2 resume：先开恢复 case

用户请求 resume 后，Run 保留 paused/blocked 的事实状态，在 AsyncOperation 中表示正在核对。不要在 API 入口直接改回 running。

恢复结果可能是：原任务仍在跑则继续观察；可证原生续接则 resume_existing；只能新会话则请求交接决定；无法核实则 needs_reconciliation。

只有恢复方案已经应用、当前授权/绑定成立且没有禁止写入的未知执行，才恢复 Run 的正常派发。依旧不能自动批准新计划或扩大原生审批范围。

### 13.3 cancel：停止请求与取消完成是两件事

同步阶段：cancel_requested + cancel_requested_at + control operation + WakeSignal。撤销尚未开始的意图，保留已经可能执行的账本。

异步阶段：请求并核对所有受影响原生执行和子执行停止。满足取消安全条件后设置 canceled，保存未交付产物、未决副作用和未知费用引用。

如果外部产品仍可能执行，Run 保持 cancel_requested；控制操作可显示 needs_reconciliation，返回未停止实例清单。平台不能说 canceled 就把关联进程记录删掉。

原生已停止但费用尚未可知，可以完成“执行取消”，但要保留费用未决账本及明确风险，不能伪造已退款或结算完成。

### 13.4 drain：关闭平台接单不是证明 Agent 停止

在既有 control/shutdown 流程上接入 platform_admission，DB 是 worker 共同读取的权威；现有 control 文件作为本机镜像/启动提示。

draining 后：不接受新 Run 执行、不派发新开发任务；Driver 可以继续处理停止/结果/恢复观察；逐项记录未完成实例和未知操作。所有发送/Runner 入口先核对环境 admission，不能只让 API 首页显示 drain。

原来的 `collect_drain_coordination` 按扁平实例 status 过滤需要改进：failed/created 也可能有已派发但未回写的操作；必须同时查未知 InstanceOperation、DeliveryAttempt、Runner 与审批回传。只有这些核对后满足安全条件才能 drainComplete=true。

平台停止后不再对外承诺持续监控；若主动停止进程时仍有未知执行，保存清单并明确下次启动必须核对。强制退出平台不等于远端 Agent 已经终止。

### 13.5 replan

调用现有 D08 重规划规则前先建立安全边界。运行中要求先停止/暂停相关旧执行；建立新 PlanRevision/Assignment 草稿后重新用户确认。新计划不继承旧计划的执行授权，旧图归档，新图绑定新版本。

## 14. API、CLI 和队列入口

### 14.1 API

沿用主契约的 `POST /api/v1/runs/{id}/actions`，实现暂停、恢复、取消和重规划。示例请求：

```json
{
  "action": "pause",
  "expectedStatusVersion": 17,
  "idempotencyKey": "pause-run-20261112-001",
  "reason": "检查当前产物"
}
```

返回 HTTP 202 和 OperationAccepted，只表示请求已持久接受。未真正停稳之前，OperationStatus 仍为 running / needs_reconciliation，不能返回 pause 成功。

新增建议接口：

| 接口 | 用途 |
| --- | --- |
| GET /runs/{id}/waits | 分页列出未决等待和安全的公开范围 |
| GET /runs/{id}/driver | 返回图版本、当前 thread 引用、最近观察序号与协调状态；不暴露 lease token |
| POST /runs/{id}/recovery-checks | 请求采集当前恢复证据，返回 operation/case 引用 |
| GET /runs/{id}/recovery-cases | 查询核对历史 |
| GET /recovery-cases/{id} | 查询观察摘要、阻塞原因、推荐动作与证据引用 |
| POST /recovery-cases/{id}/decisions | 绑定 caseVersion/contextHash/statusVersion 的明确恢复决定 |
| GET /operations/{id} | 复用或补齐现有操作查询契约，不只查询模型任务 |

查询响应应有界。D12 才实现完整一致快照与 SSE，这里不要为了显示等待列表临时实现第二套全量状态聚合。

对用户没有开放 `POST /graph/{thread}/resume` 或 `update_state` 入口。用户改变业务事实，Driver 才据此恢复图。

建议稳定错误码：driver_busy、driver_fence_lost、stale_binding、status_version_conflict、idempotency_conflict、wait_scope_mismatch、checkpoint_incompatible、native_state_unknown、workspace_mismatch、pending_side_effects、pending_stop_verification、recovery_evidence_stale、resume_unsupported、handoff_confirmation_required。

### 14.2 CLI

新增并标注是规划接口，实施后才可运行：

```powershell
agentforge run action --run-id <id> --action pause --expected-status-version 17 --idempotency-key <key>
agentforge run waits --run-id <id> --json
agentforge run driver --run-id <id> --json
agentforge run recover --run-id <id> --idempotency-key <key> --json
agentforge recovery get --case-id <id> --json
agentforge recovery decide --case-id <id> --action handoff_new_session --context-hash <hash> --case-version <n> --expected-status-version <n> --idempotency-key <key>
```

CLI 和 API 共用应用服务，不能一边走 RunControlService、一边直接修改 Run.status。CLI 输出要区分“请求已接受”“等待停止”“已暂停”“需要核对”。

新增受信维护命令用于单次补扫或 Driver 片段，例如 `agentforge driver sweep --once`；限制本机 driver 身份，不把它当可跳过授权的开发后门。

### 14.3 队列

新增 intent/task 对应关系，并为每个类型同时写路由测试：

| outbox intent | 处理器 | 说明 |
| --- | --- | --- |
| driver.wake | driver_step | 读取 signal，取得协调权，执行 drive_once |
| workspace.prepare | prepare_workspace | D07 的三段式协调器 |
| recovery.inspect | inspect_recovery | 核对原生/文件/未决账本，落观察结果 |
| instance.resume | 既有 collaboration_operation 的正式 resume 分支 | 经过核对的原生续接，不隐式 handoff |

driver_step 可以使用独立 `agentforge-driver` 队列以免耗时 native I/O 挤占协调片段；它仍是受信 driver 进程。初版也可由同一服务进程消费 driver/control 两队列，但要留出协调容量，且在接口中显式配置队列集合。

实际使用 `.configure(lock=...)` 时只把队列锁视为减少重复任务的优化，正确性依赖数据库 lease、fence 与唯一约束。不要假设队列 lock 就是 exactly-once。

定时补扫通过现有后台服务的周期任务或明确启动的 worker 周期入口实现。不要让 HTTP 请求线程 sleep，也不要靠用户一直开着某个 CLI 窗口才能恢复。

## 16. 测试要怎么写，至少覆盖这些场景

测试关注安全事实与可观察副作用，不写一堆只断言函数被调用的测试。原生替身可维护 `created_sessions`、`submitted_operation_ids`、`running_children` 等可观察状态；通过异常注入模拟“外部已执行，平台还没记账”。

| 场景 | 故障/输入 | 必须观察到的结果 |
| --- | --- | --- |
| 同 Run 两 Driver | 两线程同时过 barrier 调用 drive_once | 只有一个有效 fence/推进；另一个 busy 或稍后观察既有结果 |
| lease 失效 | 旧 Driver 暂停，另一控制者取得新 lease | 旧业务写、checkpoint put 与 put_writes 均失败 |
| 图连接断开 | 丢失持锁 psycopg 会话 | 本片段退出；不能自动重连沿用旧身份 |
| 事务后 checkpoint 前崩溃 | 已创建 Message/attempt 后终止 | 重启复用同 operation/attempt，不新增原生调用 |
| 原生后回执前崩溃 | 产品记录已 submit，进程退出 | 账本 unknown，重投不再次 submit |
| 等待时重启 | 原图已 interrupt，销毁所有内存对象 | 新实例读取 PostgreSQL checkpoint 和 wait 后继续 |
| 先事件后 wait | 事件在登记前到达 | 快照发现条件满足或补信号，不无限挂起 |
| wait 后 checkpoint 前事件 | 提交 wait 后立即写结果 | 下一片段仍可解析并恢复，不丢通知 |
| 重复唤醒 | 相同 source_ref 多次写入、队列重投 | 信号唯一；领域意图和原生动作不增加 |
| 多个未决审批 | 两实例同时 waiting_approval | 两个 wait/请求都保留；一个批准不放开另一个 |
| 下游提前派发 | 上游仅 done，没有 ReleaseRecord | 不创建下游 attempt 或任务发送 |
| 同实例两工作包 | 两个就绪任务并发预留 | 只允许一个活跃 attempt；另一等待容量 |
| unknown 工作槽 | 外部可能已执行 | 超时后仍不能重新占同一写入范围 |
| 暂停与发送竞争 | pause 提交后 Worker 才领取 | 新发送被阻止；已经可能发送的走停止核对 |
| 取消远端未停 | stopRequest ack，但 childrenRunning=true | cancel_requested / needs_reconciliation，不 canceled |
| drain 遗漏扁平状态 | instance failed/created 但 operation unknown | drainComplete=false，列出未决操作 |
| 原会话仍在运行 | 恢复 probe 有可信 running 证据 | observe_existing，submit 计数不增加 |
| 原生不支持恢复 | support=unsupported，旧执行已停止 | 要求 handoff；新会话记录明确区别于原生恢复 |
| 旧会话回写 | 新 attempt 已绑定，旧 session 发送事件 | 保存 stale 记录，不改当前生命周期/门禁 |
| 恢复中变计划 | case 生成后 plan 或 assignment 变更 | apply 冲突，旧推荐不应用 |
| 哈希变化 | 固定候选对象被换/工作区偏离 | 阻塞或返工，不复用旧通过报告 |
| 费用未知 | 调用已可能计费但无 usage | 保留预留/未知费用，不用重试产生第二次收费 |
| 登录过期 | probe 读不到产品状态 | unknown / 等授权；不解释为已停止 |
| 图 schema 不兼容 | 读取旧 state_schema_version | blocked 或已注册迁移，不自动 update_state 硬改 |
| Git 完成后断电 | 目标 worktree 存在但 DB 无完成记录 | 核对同目录身份并认领原结果，或阻塞；不创建重复目录 |
| 集成交接边界 | 所有 D10 阶段已放行 | ready_for_integration；Run 还不能 completed |

### 16.1 PostgreSQL 测试要求

租约、唯一约束、并发、checkpoint/Wait 恢复必须使用真实 PostgreSQL。内存 Ledger 无法证明这些性质。

初期可以在现有 PostgreSQL 中创建随机隔离 schema 做机制测试，但若省略外键或角色权限，报告必须注明。D11 最终验收还需要一个完整迁移和分权角色的隔离环境，不能用省略外键的测试冒充部署验收。

本方案本身不执行这些测试或迁移。实施后执行既有 Ruff/mypy/pytest，并显式运行本批 PostgreSQL 测试。需要真实产品的场景由已验证适配器和受信 Host 执行，unsupported 产品如实阻塞。

### 16.2 推荐先完成的最小纵向场景

使用一个真实临时 Git 仓库、两个工作包 A→B、受控原生替身和真实 PostgreSQL：

1. 从已确认计划建立线程。
2. 准备 A 工作区/会话，预留 attempt 并派发一次。
3. 图 interrupt，关闭 Driver 进程和连接。
4. 提交受信结构化 A 结果，完成实际文件冻结、验证及 D10 ReleaseRecord。
5. 重启新 Driver，接收持久唤醒，只派发一次 B。
6. B 运行时请求 pause，证实子执行已停后才 paused。
7. 请求 resume 并核对原生状态，按产品支持继续或明确交接。
8. B 通过 D10，生成 IntegrationHandoff；确认未提前 completed。

这个用例先跑通，再增加多角色并行和 dependency_branch。不要先写复杂动态图和大量子图。

## 17. 一个恢复例子，串起来看

假设 workPackage B 的 attempt 是 ia_B_01，产品任务已收到，但平台在回执入库前退出。

```text
数据库：delivery=unknown；attempt=dispatching/unknown；没有可信成功回执
产品：session S 中 B 仍在执行
图 checkpoint：停在 dispatch_ready 附近
```

重启后的正确过程：

1. 新 Driver 拿到协调权，加载 checkpoint，并刷新业务事实。
2. 发现同工作包有未知尝试，planner 选择 open_recovery，不选择 dispatch_ready。
3. RecoveryProbe 在事务外核对 S、真实 cwd、workspace、attempt 关联与子执行。
4. 明确原任务仍在跑，则保存观察，推荐 observe_existing。
5. 应用决定后继续接收原任务事件，原 delivery 保留真实的历史不确定性/补充对账结果。
6. 收到正式提交后走 D10 停止、冻结、验证与审核。

错误过程是“checkpoint 没有成功标记 → 认为没做过 → 新建会话再发一次”。D11 要用数据库唯一约束、unknown 工作槽和恢复协议共同禁止这种行为。

## 18. 开发时的完成标准与边界

D11 完成至少应交付：

- 一份稳定的协作图定义与版本策略，节点调用已有领域服务。
- 能跨进程读取的 PostgreSQL checkpoint 与等待记录。
- Run lease、业务 fence、checkpoint fence 和图调用串行化。
- 有界 Driver、可去重唤醒、补扫和明确的未知结果处理。
- 工作区/实例/任务/提交/门禁/返工的完整自动协调链。
- RecoveryCase 的观察、策略、决定和原生续接/新会话交接。
- pause/resume/cancel/replan、平台 drain 的真实完成条件。
- API/CLI、契约导出、迁移/角色说明与故障测试证据。

以下能力不应顺手扩大为本批必须重写：外部 Agent 的模型工具循环、独立分布式 DAG 引擎、自动任意工具执行、向量记忆、最终 SSE 系统、最终集成验收、自动 git push/部署。

若真实产品当前仍报告 unknown/unsupported，可以完成平台机制与替身/数据库测试，但 R14 的真实产品证据仍应标待验收，不能将“代码路径存在”当作“产品已支持”。

## 19. 开始写代码时，第一步具体做什么

从 D11-01 开始，先创建 `contracts/collaboration.py` 与 `contracts/recovery.py`，写清 GraphBinding、WaitReason、WakeSignal、RecoveryObservation、RecoveryRecommendation、RunControlRequest、DriverResult。
