## 1. D12 到底解决什么问题

D11 的终点是：用户确认的协作计划已执行，各阶段按 D10 规则放行，形成固定候选和版本的 IntegrationHandoff。它没有证明所有角色的产物合在一起之后仍然正确，也没有代替用户接受成果。

D12 要把下面这条链做完整：

```text
同一数据库视图下的运行状态与事件游标
             ↓
客户端从游标补读已提交事件，断线后可以继续
             ↓
选择 D11 交接中的已放行成果，构造独立集成版本
             ↓
在这个固定版本上运行整体检查和最终审核
             ↓
发布不可变交付 manifest，用户接受/拒绝/部分接受
```

例如：后端角色和测试角色各自通过阶段门禁，但整合后导入路径不一致，整体测试失败。D12 必须显示“集成检查失败”，不能因为两个阶段都 released 就让 Run completed。修复之后产生新集成版本，旧版通过记录和旧用户确认也不能套到新版本上。

### 1.1 本批目标和边界

本批交付：

- 一致的运行摘要和按需分页明细。
- 三类 Agent 数量及其统计口径。
- 基于 PostgreSQL 事件账本的 SSE、补读、重同步和有界连接管理。
- 固定输入选择、独立集成构建、集成版本与内容证据。
- 真实受控整体检查、最终审核、不可变交付 manifest。
- 绑定准确版本的完整/部分用户验收与历史查询。
- 查询、事件、集成和验收 API/CLI 以及故障测试。

本批不自动 git push、不部署、不操作用户主工作区做破坏性合并。接受成果仅表示用户的交付决定，不能隐含外部发布授权。Markdown/PPTX 的专用业务验证器仍按 D13 注册；D12 不用文件存在或 UTF-8 校验冒充它们的内容正确性。

### 3.1 对照具体代码机制再落地

课程 s13 深入部分提到 `ShellCommand.background(taskId)` 将输出转到文件、`enqueueTaskNotification` 和 `messageQueueManager.ts` 发送完成通知。D12 对应写法是：`process_integration_check` 记录受信执行结果，日志存储返回 logId，事务中写 `integration.check_completed`，SSE 只发送摘要和可授权查询的引用；不复制课程里的内存结果字典。

课程 s16 深入部分讨论 `teammateMailbox.ts` 的结构化协议与 requestId 关联，并强调消息流程和执行拦截是独立机制。D12 对应先在 `submit_final_review` 验签和匹配完整请求，再由 `evaluate_integration_cycle` 判定技术门槛；用户验收仍由另一个带版本条件的 `decide_acceptance` 执行。

课程 s18 深入部分区分会改变当前会话 cwd 的 EnterWorktree 与子 Agent 的 `cwdOverridePath`，并单独持久化工作区状态。D12 对应使用显式 workspace_id/cwd 的集成执行上下文，不对 API/多任务 Worker 调用全局 `os.chdir()`；所有树读取都来自固定快照。

SSE 不是照搬 CC 的 token 输出流。这里由平台已经提交的领域事件驱动状态；token/日志只做暂态观察，不能决定阶段和运行完成。教学版 JSONL/内存通知队列也不替代 PostgreSQL 的事件和操作账本。

## 4. 先区分五种“完成”

| 事实 | 判定依据 | 不能推出什么 |
| --- | --- | --- |
| 原生任务结束 | 受信原生事件/检查 | 不等于提交完整、停止已证实或阶段放行 |
| 阶段已放行 | 当前版本 D10 ReleaseRecord | 不等于组合后的代码通过整体测试 |
| 集成版本技术通过 | 同一版本、策略和环境的必需整体检查及审核全部满足 | 不等于用户接受 |
| 用户接受 | 当前 manifest/integrationVersion 的持久验收决定 | 不等于 push/deploy 得到授权 |
| Run completed | 当前版本全部必需成果技术通过且完整接受，且无冲突的活动执行 | 不等于所有可选成果都已成功，也不改变失败历史 |

部分接受只记录用户接受的合法子集和剩余范围，不把被拒绝/失败项标通过。初版部分接受不将 Run 设为 completed；显式“关闭并保留部分成果”的产品流程若以后需要，应单独设计，不能偷用 completed。

### 4.1 版本命名

- `integrationId`：一次构建操作/低层 GitIntegration 的身份。
- `integrationVersion`：不可变集成内容身份，对应 IntegrationVersionRow.id；同一源代码字节、基线和输入选择的确切绑定。
- `validationCycleId`：该版本在某个确定检查策略/环境下的一轮检查与审核。
- `manifestRevision`：交付说明/证据集合的不可变修订号；重跑检查可形成新修订，不偷偷覆盖旧文档。
- `manifestHash`：该 manifest 规范化内容的 SHA-256。
- `deliveryRevision`：Run 当前交付指针的并发版本；新版本、撤回或失效时提高。
- `statusVersion`：Run 业务并发版本；不能用 SSE sequence 代替。
- `latestSequence`：快照事务能看见的最后一个已提交运行事件序号。

## 6. 契约与数据模型先怎么写

### 6.1 RunSnapshot 的形状

保留已有 RunSnapshotResponse 的公开字段，增加有界摘要。不要直接把所有 ORM 对象序列化给客户端。

```python
class RunSnapshot(ContractModel):
    schema_version: str
    run: RunOverview
    binding: ExecutionBindingOverview
    agent_counts: AgentCounts
    stage_summary: StageSummary
    progress: ProgressSummary
    current_delivery: DeliveryOverview | None
    wait_summary: WaitSummary
    latest_sequence: int
    latest_event_id: str | None
    replay_floor_sequence: int
    snapshot_token: str
```

`run` 包含 status/statusVersion/planVersion/assignmentVersion/gatePolicyVersion/activeGeneration 等；`current_delivery` 包含 currentIntegrationVersion、manifestHash、technicalStatus、acceptanceStatus、deliveryRevision；摘要都有显式 schema 和体积上限。

`snapshot_token` 绑定 run、latestSequence、查询范围、schemaVersion、过期时间和必要版本，采用既有受信密钥机制签名。它用于分页/重同步绑定，不授予权限；不放用户 bearer。可以只给分页使用这个 token，不要求所有 SSE 连接额外校验它。

已有 GET /runs/{id} 若未发布可整体调整并更新调用方；若已有兼容使用方，推荐保留现有顶层字段并增加摘要，或新增 `/runs/{id}/snapshot`，由 GET /runs/{id} 委托相同查询服务。不要同时维护两个不一致的快照实现。

### 6.3 事件类型要跟实现一起注册

建议复用已有 `run.status_changed`、`integration.validated`、`run.delivery_ready`，另按实际链路增加 `integration.build_requested/built/conflicted`、`integration.check_completed`、`integration.review_completed`、`delivery.manifest_published/invalidated`、`acceptance.decided` 及公开投影 `state.invalidated`。这些名称是待实现契约，必须同时注册 payload、公开字段投影和测试；不能 Worker 开始写了字符串，但 SSE/schema 还不认识。

`integration.validated` 只能在真实 policy evaluator 得出结论后产生，不由客户端传入 passed 决定。每条事件说明绑定哪个 version/cycle/manifest；不会把连接断开和 token 结束映射成此类业务事件。

### 6.4 约束的两个注意点

第一，IntegrationVersion 的树内容和源输入不能更新。检查结果通过独立 cycle/report 追加；“当前报告集合”是查询投影，不能修改旧版本内容后仍沿用相同 versionId。`status` 等构建/验证状态存在 operation/cycle 或当前投影里，不能把源树身份和可变验证进度写成同一份可覆盖 JSON。

第二，验收决定本身不属于技术检查。即使用户拒绝，也不把 passed 改 failed；即使用户接受，也不把 failed/not_run/unknown 改 passed。技术状态和用户决定分别保存。

## 7. 一致状态查询：具体怎么实现

### 7.1 SnapshotQueryService 用一个短只读事务

新增：

```python
def load_run_snapshot(
    engine,
    *,
    principal: AuthenticatedPrincipal,
    run_id: str,
) -> RunSnapshot: ...
```

使用 PostgreSQL REPEATABLE READ + READ ONLY，在同一连接/事务里完成权限、Run、当前计划/分配、阶段/候选摘要、当前交付、wait 和 latestSequence 的读取。PostgreSQL 的 READ COMMITTED 每个语句可以看到不同快照，不能满足这里的组合查询要求。[S5]

示意：

```python
with engine.connect().execution_options(isolation_level='REPEATABLE READ') as conn:
    with conn.begin():
        conn.exec_driver_sql('SET TRANSACTION READ ONLY')
        with Session(bind=conn, autoflush=False, expire_on_commit=False) as session:
            authorize_run_read(session, principal, run_id)
            run = load_run(session, run_id)
            result = build_bounded_snapshot(session, run)
            # 在事务内完成 DTO 构造，不能返回待 lazy load 的 ORM 对象。
```

所有查询使用这个 session，不在 build 函数内部又打开其他 engine/session。不要在事务中读取原生产品、遍历文件、等队列、解析大报告或执行模型调用。

`latestSequence` 读取本事务中的 Run.last_sequence；`latestEventId` 对应同 Run 同序号事件，0 时为 null。发现最后事件缺失且不在已记录归档范围内，应报告存储异常，不编造 eventId。

### 7.2 事件写入要满足查询的前提

如果实例状态已经提交，但事件要另一个事务才插入，客户端可能拿到新状态/旧游标，后续无法正确解释。整理现有两个事件入口，使它们都遵守：

```text
Run 行锁 → 领域状态修改 → 类型校验 → 分配 sequence
→ Event + 必要 outbox/WakeSignal → 同事务提交
```

回滚也回滚 sequence；全量可补读业务事件应在每 Run 内连续，不用数据库独立 sequence 预分配导致空洞。`append_fact` 的 flush/refresh 保护不能丢。

并非每条 Event 都需要 queue outbox。SSE 直接读已提交 Event；不要给所有事件写一个没有消费者的 target=sse outbox。需要唤醒 D11 的事件按其 allowlist 单独生成。

只向客户端发送提交后可见的事件。数据库通知若后续引入，仅负责唤醒读取，不能在事务提交前把 payload 推给客户端。

### 7.3 大型列表和分页

快照只含摘要，列表使用 keyset 分页：

- 实例/消息按 `(created_at, id)`，不以可变 status 排序。
- 事件按 sequence。
- 版本按 version_number。
- 报告按固定 cycle 下的 `(created_at, id)`。

游标绑定 run、资源类型、过滤条件哈希、排序方向和上限，签名后仍需每次认证。参数化 SQL，不把客户端 orderBy 拼成 SQL 片段。

不要声称多个 HTTP 分页请求共用第一次数据库快照。初版提供两种清晰语义：

1. 不可变资源（固定 manifest、version、cycle 的报告）按绑定 ID 分页，可稳定读取。
2. 可变资源（当前实例/等待状态）为每页的当前视图，响应返回 pageAsOfSequence 和 bindingRevision；若调用方要求与某个 snapshot_token 精确一致，而关联业务版本已经变化，返回 snapshot_stale，要求重新加载。不能拿新页偷偷拼成旧快照。

不保持跨请求的长数据库事务，也不为每个客户端长期 export PostgreSQL snapshot。若未来必须提供大型精确快照，可额外持久化受限查询投影，另做保留策略。

### 7.4 三类 Agent 数量怎么计算

`queries/agents.py` 新增：

```python
def summarize_agent_counts(session, *, environment_id, run_id, as_of) -> AgentCounts: ...
def explain_profile_schedulability(session, profile, required_capabilities, as_of): ...
```

| 字段 | 定义 | 不能用什么代替 |
| --- | --- | --- |
| discoveredProductCount | 选定环境中已发现且未被明确移除的不同 product_id 数量 | 安装路径数、角色数或 profile 行数 |
| schedulableProfileCount | 登录有效、配置/能力证据绑定且未过期、匹配所需能力，并满足当前授权与容量约束的不同 profile 数量 | 全部 AgentProfileRow 数量 |
| activeInstanceCount | 当前 Run 中有可信活动会话的实例数量，按明确 lifecycle 集合计算 | 窗口数、profile 数或仅 status='running' |

同时返回 product/profile/instance 的分类计数，如 manualAssisted、limitedAuto、busy、waitingApproval、stopped、unknown、needsReconciliation。unknown 单列，不能混进已停止或可调度。并发占满的有效 profile 可以列为 verifiedButBusy，避免用户把“暂时不可调度”理解成产品不存在。

可调度判定复用 D09 能力规则，拆出无副作用的证据评估函数，不在只读统计中执行 validate_capabilities 或获取写锁。真正派发继续调用原来的严格验证。

统计必须带 environmentId、requiredCapabilities、asOf 和 inventoryRevision。某 profile 是否适合“当前待派发角色”与是否适合泛化功能不是同一问题，响应中说明 scope。

全局产品发现/登录变化不天然属于一个 Run 的事件序列。初版把库存统计放在独立 `/agents/summary`（带 inventoryRevision/asOf），Run 快照引用该事务所见库存版本；run SSE 只保证 Run 领域事实的补读。CLI 需要实时库存时按独立摘要定期刷新，不能宣称 Run.sequence 覆盖所有环境目录变化。影响当前已分配角色的配置/授权失效仍须由 D11 记录 Run 阻塞事件。

### 7.5 进度不凭 token 或时间估算

ProgressSummary 返回 workPackages：total/ready/running/submitted/released/blocked/failed，以及 finalChecks、finalReviews、acceptance 的数量。

初版不提供误导性的一个百分比；需要时只给明确定义的 `releasedRequiredPackages / totalRequiredPackages`，并标为阶段协作进度。它达到 100% 也不等于集成检查与用户验收已经完成。只有失败/返工后原进度真实变化时才更新，不为了界面好看强制单调上升。

## 8. SSE 游标与连接协议

### 8.1 保留现有 eventId 语义

当前 `SseCursorSemantics` 明确 Last-Event-ID 对应 eventId，sequence 用于排序和补读。沿用它：

```text
SSE id: <数据库 Event.event_id>
业务 envelope.eventId: 同一个 Event.event_id
业务 envelope.sequence: 同 Run 内递增整数
```

不能一处用 evt_xxx、一处用 run:sequence，客户端重连会失配。

首次连接：先 GET 快照，再调用 `GET /runs/{id}/events?afterSequence=<snapshot.latestSequence>`。这个 query 参数是无秘密的读取游标，不是 token。

重连：CLI 发送 `Last-Event-ID: <最后成功应用的事件 ID>`。实现：

```python
def resolve_event_cursor(
    session,
    *,
    run_id: str,
    last_event_id: str | None,
    after_sequence: int | None,
) -> ResolvedCursor: ...
```

规则：

1. 先认证并校验 Run 读取权限，再查 cursor。
2. header 限长并拒绝 CR/LF/NUL；ID 作为不透明值精确匹配，不从其字符串猜 sequence。
3. 找到 event 后核对 event.run_id 等于当前 Run；不匹配返回 cursor_scope_mismatch。
4. afterSequence 要求严格非负整数且不大于当前事务 latestSequence；超前返回 cursor_ahead。
5. 两种参数都给时解析后必须一致，否则 cursor_conflict；初版也可以直接拒绝混用，但前后端和测试必须统一。
6. 首次连接两者都没有，返回 snapshot_required，而不是偷偷从“现在”开始导致漏状态。
7. header 对应 ID 已归档/查不到：返回 resync_required 控制帧并结束流；不把它当 sequence=0。错误 ID 不提供其他 Run 的内容。

快照序号为 0 时可以 afterSequence=0。快照 latestEventId 只是便利字段；事件归档之后仍可使用快照的数字 afterSequence 检查窗口。

### 8.2 SSE 数据帧

```text
id: evt_example
event: stage.released
data: {"schemaVersion":"1","runId":"run_example","sequence":42,...}

```

实现 `encode_business_event(envelope) -> bytes`，所有字段从行首开始。Python 字符串使用换行转义生成真实换行；输出以空行结束，不能发送字面量反斜杠 n。

```python
def encode_business_event(envelope) -> bytes:
    body = json.dumps(
        envelope.model_dump(mode='json', by_alias=True),
        ensure_ascii=False,
        separators=(',', ':'),
    )
    return (
        f'id: {envelope.event_id}\n'
        f'event: {envelope.type}\n'
        f'data: {body}\n\n'
    ).encode('utf-8')
```

event.type 只能来自注册枚举，event_id 禁止换行。payload 中的用户文本由 JSON 编码，不直接插到 SSE 字段行里。响应 Content-Type 为 `text/event-stream; charset=utf-8`，Cache-Control no-store；部署时禁代理缓冲/压缩聚合，并验证实际效果。[S4]

### 8.3 心跳和控制帧独立于业务事件

心跳使用注释行：

```text
: heartbeat

```

不写 Event、不生成 eventId，不推进 sequence。

resync_required、auth_revoked、server_draining 等连接控制帧使用单独 SseControlFrame schema，**不带 id、不带伪造的 EventEnvelope.sequence**。例如：

```text
event: resync_required
data: {"schemaVersion":"1","reason":"cursor_expired","snapshotUrl":"/api/v1/runs/run_example"}

```

现有 EventType 中有 resync_required 历史定义，要明确其在流中是控制语义；不能为了满足 EventSequence>=1 随手造一个 Run 事件或提高 last_sequence。兼容模型仍可保留，但 serializer 分开。

标准 SSE 中不发送 id 的帧不会把最后事件 ID 清空；客户端仍要按业务协议在 resync_required 后主动重取快照。[S4]

### 8.4 客户端如何处理重复和乱序

定义 ClientRunProjection(appliedSequence, lastAppliedEventId, snapshotBinding)。每个事件先检查 run/schema，再处理：

- sequence <= appliedSequence：重复/过期，忽略，不回退。
- sequence == appliedSequence + 1：应用注册 reducer；成功后才更新游标。
- sequence > appliedSequence + 1：不拿后面的状态硬填缺口，补读或重新取快照。
- 不认识 schema/type 或公开投影版本：重同步/升级客户端，不直接跳过后继续声称完整。

初版 SSE 事件主要负责通知哪些状态变化了。复杂事件可以触发重新查询相关摘要，不强求所有业务都实现本地 reducer。重新快照也必须原子替换本地视图和 appliedSequence，不能先改游标后发现解析失败。

浏览器原生 EventSource 不提供任意 Authorization 请求头配置。当前项目采用 Bearer、禁 token query，且没有本批前端任务，因此 CLI 使用 httpx streaming；未来浏览器使用受支持的 fetch 流方案和明确 Origin 策略，不能把 bearer 塞进 URL 来适配 EventSource。[S4]

## 9. SSE 服务怎样避免占满资源

### 9.1 PostgreSQL 是补读权威，初版不加 Redis

新增 `EventStreamService.iter_frames` 异步生成器。每轮调用一个短只读查询取有界 Event DTO，关闭 Session/连接之后再 yield。下一轮从最后送出的 sequence 继续读。

```python
async def iter_frames(self, request, principal, cursor):
    try:
        while not self.deadline_reached():
            if await request.is_disconnected():
                return
            await self.ensure_current_authorization(principal)
            batch = await self.read_bounded_batch(cursor)
            if batch.resync_required:
                yield self.encode_resync(batch.reason)
                return
            for event in batch.events:
                yield self.encode_public(event)
                cursor = cursor.after(event.sequence)
            if not batch.events:
                if self.heartbeat_due():
                    yield b': heartbeat\n\n'
                await self.wait_for_next_poll()
    finally:
        await self.release_stream_slot()
```

这个骨架省略具体错误映射和期限计算。实现时 read_bounded_batch 必须通过线程池运行现有同步 SQLAlchemy，或使用独立经过验证的异步存储实现；不能在 async generator 中直接执行阻塞查询。线程函数内建立/关闭 Session，返回普通 DTO，不跨线程传 Session。

wait_for_next_poll 是可取消的异步等待，等待时不持数据库连接。数据库故障先有限退避，超出流期限关闭，客户端用旧游标重连；不能插入一条假的“业务失败”事件。

### 9.2 起始限制

这些是本机开发起始配置，实施后需实测，不是容量承诺：

| 项目 | 初始值/策略 |
| --- | --- |
| 每次读取 | 最多 100 条，编码后总量最多 256 KiB |
| 单条公开事件 | 最多 64 KiB；写入时就限制，超大正文放对象存储并只带安全引用 |
| 空闲轮询 | 约 1 秒，可取消；不忙等 |
| 心跳 | 约 15 秒 |
| 活跃连接重新认证 | 每批且空闲最长约 5 秒再查一次 |
| 单连接最长存活 | 约 5 分钟，结束后可用游标重连 |
| 应用发送超时 | 约 10 秒无发送进展则关闭 |
| 连接上限 | 配置总量和每凭据上限，例如初始总 10/每凭据 2；超限 429 |
| 客户端状态缓存 | 只保留有界 ID/摘要；不在内存无限积累历史日志 |

服务器单次读取的“条数/字节”限制是有界回放，不是删事件。如果第一条就超过预算，不能永远返回空批；必须通过既有投影压缩为安全引用，或发送 resync/error 控制并停止，暴露数据格式问题。

`yield` 受背压不代表网络发送一定有超时。使用 StreamingResponse 时增加实际 ASGI send 超时包装（或经验证支持该语义的 SSE 组件），例如在 `http.response.body` 的 await send 周围使用 AnyIO fail_after。连接长期不读就取消流并释放资源。不能只设置 httpx 请求超时来声称服务端已解决慢客户端。

不为每个连接建立无限 asyncio.Queue。数据库事件账本已经承担持久缓冲，慢客户端重连补读即可。日志/token 洪峰不能阻塞领域事务。

### 9.3 权限撤销在长连接期间生效

现有认证依赖返回 None，会丢失调用者身份；改为生成 AuthenticatedPrincipal，至少保存 credential_id/version/scope，并在 request.state 注入。验收 actor 也复用这个主体，不能用请求体 userId 或固定 user:api 充当审计身份。

流中重新核对凭据撤销/过期和资源读取范围。可重用 CredentialVerifier；若重验需要原 bearer，仅在本次请求内存保存，禁止写 DTO、日志、snapshotToken 或 query。注册表的撤销和环境配置 token 的重载方式要区别说明；环境 token 不支持实时配置热加载时，流最长生命周期提供清晰上界。

权限撤销后不再发业务数据，能安全发送则发不含资源详情的 auth_revoked 控制帧，然后结束。响应头已发出后不能改 HTTP 401；只能关闭流。还未开始流的认证失败正常返回 JSON 401/403。

目录 grant 撤销不自动等于所有审计元数据不可查看：由权限策略决定可见摘要/内容，但继续开发一定受 D11 约束。不要每次读取失败就自动启动恢复或扫描项目文件。

### 9.4 公开事件投影

数据库事件可能含内部标识与证据引用，不能默认整行返回。每个类型注册 PublicEventProjector，输出字段白名单；密钥、原生 token、长命令输出、完整私密路径均不能进入公开 SSE。

同一个 Run 授权的完整事件流需维持可解释的序号连续性。内部事件可投影为无敏感详情的 `state.invalidated`（明确 schema，仍带原 eventId/sequence），而不是悄悄丢掉该序号。查询其他项目/用户的事件完全禁止；不能用占位帧透露未授权资源。

未注册的事件类型不默认透传，也不能无声跳过。记录安全错误引用并要求重同步，修复投影覆盖测试。逐项检查事件字段的授权与大小。

## 10. 保留窗口和 resync_required

`replay_floor_sequence = F` 定义为“允许 afterSequence >= F；小于 F 的补读需要快照”。若在线事件保留 F+1 之后，afterSequence=F 仍合法。

不要将表为空时 min(sequence)=null 解释成没有历史；水位持久化独立存在。watermark 也不能大于 Run.last_sequence。

`read_bounded_batch` 在同一 REPEATABLE READ 短事务中读取窗口、Run 最新序号和事件：

1. cursor < floor：resync_required。
2. cursor > latest：cursor_ahead。
3. cursor == latest：当前无新事件。
4. cursor < latest，却没有下一条连续事件，且不属于明确归档边界：gap_detected，要求快照并记录完整性故障。

在线清理不能边删边让 reader 猜窗口。后续启用时流程是：固定待归档连续范围 → 写入可验证归档并确认其可读 → 短事务锁 Run/窗口、校验范围、更新 floor 并删除该范围在线副本。清理不能触碰仍需保留的审核/验收/恢复审计引用；必要时按审计策略保留权威归档。

初版可以仅配置回放窗口、不物理删审计 Event。EventId 找不到时也回 resync，而不是伪造 eventId → sequence 映射。若以后要长期解析被删除的 ID，再增加受控游标索引或归档索引，不先创建无限墓碑表。

快照取到 N 后、连接 SSE 前窗口已经推进超过 N，也必须 resync，再取一次快照；不能跳到最新事件掩盖缺失。客户端指数退避，防止服务端频繁清理造成无限紧循环。

## 11. 集成输入选择：D10 放行的到底是什么

### 11.1 从 D11 交接构造不可变 selection

新增：

```python
def create_selection(
    session,
    *,
    principal,
    run_id: str,
    handoff_ref: str,
    expected_handoff_hash: str,
    expected_status_version: int,
    idempotency_key: str,
) -> IntegrationSelection: ...
```

在短事务中锁 Run，核对当前计划/分配/门槛、D11 交接哈希、所有必需阶段的当前放行事实。固定下列数据并规范化哈希：

```text
run / plan / assignment / generation / contractHash
baselineId + baselineTreeHash + managedDirtySnapshotRef（如有）
每个输入的 releaseRecordId / candidateSetHash / candidateId / contentHash
代码输入的 workspaceSnapshotId / snapshotManifestHash / sourceBaseHash
允许集成的路径、删除记录、工作包、角色、依赖和合成顺序
mergePolicyVersion + integrationPolicyHash
```

只有在 ReleaseRecord 的实际范围内、对象和来源均存在的输入才能被选。`shared_interface_still_blocked` 或依赖未满足时阻塞。不要允许用户随手传任意 workspaceRoot 或 lastSnapshot。

同 key 同规范内容复用原 selection，不同内容冲突。选择记录不可改；换候选或基线就新建 selection。

### 11.2 文件候选和完整代码树不能混淆

D10 的候选可能仅代表某个交付文件。一个文件通过，不意味着该工作区里所有未声明的代码、删除和临时文件都被批准集成。

因此先区分：

- 文档/单文件成果：使用已放行候选对象，只合成批准路径。
- 软件代码成果：需要固定完整树或经批准的变更清单，并能证明每个被应用的变更属于放行范围。

若当前 ArtifactContract / ReleaseRecord 不足以表达代码树范围，新增有版本的 SourceTreeContract / ReleasedTreeRef，或者将范围清单作为原计划契约的一部分重新确认。不能在 D12 私下把单文件放行升级成全目录授权。

D11 交接缺少固定工作区快照时，可以请求受控 freeze：先证明该 attempt 的写入已静止，再调用 D07 固定快照；核对快照里被选路径与已放行候选逐项一致。若想集成额外改动，需要回 D08/D10 确认和放行。freeze 无法补出缺失的审批范围。

### 11.3 同一个被确认的基线

不要在构建时用可移动 HEAD。固定 baseline.git_commit/tree，并核对实际对象存在。若计划包含 managed_dirty_snapshot，要把它纳入基线树：

```text
基础 commit + 已确认 dirty snapshot → baselineTreeHash
```

不能一边声明包含用户原始未提交修改，一边从干净 commit 开始集成。dirty 策略 blocked 时保持阻塞，不静默选择 commit_only。

## 12. 集成构建：怎样复用和修改 D07

### 12.1 先补 Engine 协调器

当前 `api/git.py` 在 UOW 中直接调用底层 integrate；该方法会运行 Git、解包和写文件。D12 不应直接从 HTTP 长事务调用它并宣称已经有持久恢复能力。

新增：

```python
def request_integration_build(engine, *, run_id, selection_id, request_key): ...
def process_integration_build(engine, settings, *, build_id): ...
def reconcile_integration_build(engine, settings, *, build_id): ...
```

分三段：

1. **短事务**：锁 Run，核对 selection/授权，预先分配 build_id、受控 workspaceId/路径，写 integration_build 和 outbox，提交。
2. **事务外**：领取意图提交后执行 worktree、受限差量合成、对象存储写入。结果可能未知时不按 claim 租约再次随机创建工作区。
3. **短事务**：核对 claim/binding 与实际工作区/快照结果，保存 GitIntegration、IntegrationVersion 与事件/outbox；如果绑定过期，只归档本次结果，不替换当前交付指针。

target 路径以固定 build_id 导出，Worker 崩溃后检查同一个目录的 Git common dir、基线、source bindings、目录身份、内容 manifest。单个 marker 不能证明归属；不一致进入 D11 recovery，不能删除目录后假装第一次执行。

### 12.2 将“全树覆盖”改成基于固定基线的变更合成

现有 D07 声明 full-tree overlay。D12 的语义必须更严格：角色快照中未改动的基线文件不能被当作一次写入，覆盖或冲突掉另一个角色的真实修改。

新增纯函数：

```python
def compute_tree_delta(base: TreeManifest, candidate: TreeManifest) -> TreeDelta: ...
def combine_approved_deltas(
    base: TreeManifest,
    inputs: tuple[ApprovedTreeDelta, ...],
) -> MergePlan: ...
def materialize_merge_plan(plan: MergePlan, *, destination, object_store) -> BuildResult: ...
```

每个 delta 的元素包含 path、kind(add/modify/delete)、expectedBaseHash/mode、newHash/mode、sourceRef。只读取固定对象和批准路径，不能临时重新扫角色当前目录作为来源。

默认冲突规则：

- 一个角色改动、另一个仍保留基线原文：保留真实改动，原文不构成冲突。
- 两个角色对同一路径产生完全相同的新内容/模式：可去重，记录两个来源。
- 两个不同新内容：冲突，保留来源，不能后写覆盖前写。
- 一方删除，另一方对同一路径修改：冲突。
- 两方都删除：可以合并。
- 文件/目录冲突、Windows 大小写碰撞、Unicode 规范化碰撞：明确阻塞。
- symlink/junction、submodule、无法表达的文件模式：按当前验证支持矩阵拒绝，不能丢失后继续报成功。

如果后一个阶段明确修改前一个阶段的同一文件，需要有批准的谱系：sourceBaseHash 等于前一次结果、新候选与依赖都已经过相应放行，才能按链应用。不能仅凭 mergeOrder 声称后者天然覆盖前者。

初版不自动执行 git merge -X ours/theirs，也不让模型在构建 Worker 中偷偷修冲突。冲突作为 integration build 的明确结果，回到定向返工或计划变更。修复后用新 selection/version；旧版本和证据保留。

### 12.3 内容身份与包字节身份分开

至少保留：

- `treeManifestHash`：规范目录项清单的哈希，项含规范相对路径、内容哈希、文件模式及策略版本。
- `contentHash`：内容存储中的实际归档 blob 哈希。
- `commitOrTree`：若生成 Git 对象，可用准确 commit/tree ID；没有就明确为空，不伪造 commit。

压缩包时间戳等元数据可能导致相同树生成不同 blob，不能用压缩包字节差异误认源码变了。优先生成确定性归档，树哈希始终以规范 manifest 判定。

现有 `git/snapshot.py` 读取全树文件到内存，对大项目需要加文件数量、单文件/总字节上限并改为流式/分块对象处理。超限报 blocked，不让本机多个集成耗尽内存。初版集成并发从 1 开始，实际限制由配置和验证结果决定。

## 13. 整体检查：要新写哪些代码

### 13.1 先确认检查策略来自哪里

新增 `IntegrationCheckPolicy`，包括 required checks、required review roles、配置、超时、测试数量要求、隔离/网络能力要求、允许的输出目录和失败处理。

策略必须来自用户确认的计划/交付契约。若当前 PlanSpec 没有这些字段，扩展其版本并重新确认，或新增独立 DeliveryPolicy 的草稿/确认流程。不能到最后临时默认“跑 sha256_presence 就算软件验收完成”，也不能允许客户端把 required 改 false 绕过失败。

策略编译方法：

```python
def compile_integration_policy(
    plan_spec,
    delivery_policy,
    check_registry,
    environment_capabilities,
) -> CompiledIntegrationPolicy: ...
```

缺验证器、配置非法、无需要的隔离能力、必需检查为空且无明确的非软件适用说明，都应 needs_input/blocked。平台自己的 pytest 通过不等于用户项目的整体检查通过。

### 13.2 CheckRegistry 要有真实执行语义

新增：

```python
class RegisteredIntegrationCheck(Protocol):
    check_id: str
    version: str

    def validate_config(self, config: dict) -> CheckConfig: ...
    def required_capabilities(self, config: CheckConfig) -> frozenset[str]: ...
    def build_execution_request(self, context, config: CheckConfig) -> ApprovedCheckRequest: ...
    def parse_result(self, execution, evidence_store) -> CheckOutcome: ...
```

首个可实现适配器是 `python_pytest_v1`，但只有执行边界经过验证后才标 supported。config 可包含受限 testPaths、markers 的允许子集、maxDuration、minimumCollectedTests、允许的 skipped/xfailed 策略。实际 argv 由注册器构造，绝对解释器路径和依赖锁版本固定；外部不能提交任意 shell 命令。

报告至少包含 collected/passed/failed/errors/skipped/xfailed/xpassed、exitCode、timedOut、terminationConfirmed、treeHash、环境和配置指纹。退出码为 0 不足以独自证明有测试执行；零测试、全部跳过或必需场景未覆盖按策略 blocked/failed。

项目需要 mypy/ruff/build 等检查时逐个实现有版本适配器。不要把本仓库的具体工具命令硬编码成所有用户项目的验收规则。

### 13.3 Runner 扩展与执行边界

当前 run_approved_check 只有 path_exists/file_sha256。可以增加新的 registered integration_check profile，或为旧 profile 增加严格 typed checkId 分支，但必须同步权限、ticket digest、Runner 路径和进程管理。

关键字段进入 ActionDescriptor/digest：versionId、treeHash、checkId/version、configHash、environmentRef、argvDefinitionHash、输出范围、时限、网络/文件系统策略。签发前和执行前都核对，不能仅在 API 输入时检查一次。

`subprocess(..., shell=False)` 和独立 cwd 本身不是 OS 沙箱。pytest、构建脚本会执行项目代码，可能读取环境/联网/写其他路径。因此：

- 自动受限模式必须使用已经实测的容器或受限执行 Host，并证明文件系统/网络/子进程限制。
- 当前 run_in_container 标 blocked 时，继续 blocked，不自动回落到宿主执行。
- 若产品允许明确的宿主模式，必须如实标为按当前用户权限运行，并使用相应授权；不能宣传为受限沙箱。
- 执行进程不接收用户 API bearer、数据库/队列连接、内部签名密钥；环境只注入检查所需白名单。
- 依赖安装是独立授权的操作；测试 Worker 不偷偷 pip install 或联网拉取工具。
- 超时后核实整个受管子进程树静止，结果未知记 needs_reconciliation，不只杀一个 PID 就复用工作区。

复用 D05 的票据和 D11 的未知副作用恢复机制，不在 Graph/HTTP 中直接 Popen 任意文本。

### 13.4 测试输入只读，输出与源码分开

从不可变集成快照准备检查环境。推荐输入只读挂载，输出指向 scratch/checks/<checkRunId>；Python 缓存、pytest 缓存、临时文件、JUnit 均落 scratch。实际只读限制由执行环境证明，前后哈希复核只负责检测改变，不能代替访问限制。

若某个构建工具必须修改源码目录，使用该版本的受控临时副本，记录输入树哈希与所有修改，最终报告仍绑定初始版本；最终交付不能悄悄采用测试副本改动。需要交付这些改动必须新建 integrationVersion 并重新检查。

运行前和完成后验证源 manifest；输入被更改即 report invalid，不保留之前的 passed 状态。

### 13.5 报告和日志分开保存

日志通过有界文件/对象存储保存，stdout/stderr 持续读出到受限存储，达到上限记录 truncated 并继续排空/停止，不能让无限内存 capture_output 卡住业务进程。

JUnit 等结构报告用 defusedxml/安全解析器，限制字节数、元素数量和嵌套；不执行 XML 外部实体，不信任报告里的绝对路径或命令。单个 check_id 的报告适配器只解析预期格式。

输出/报告不是可信指令。结构报告必须同时与受信执行回执、实际 command definition、退出情况和 treeHash 对齐，不能直接读取一个 Agent 写的 passed.json 就宣告通过。

`queries/logs.py::read_log_slice(log_id, offset, limit, principal)` 按 ID 授权，限制片段/返回字节；日志不是 SSE 正文。HTTP 响应做安全 Content-Type 和内容处理，不执行仓库 HTML/Markdown 脚本。

### 13.6 检查操作仍然三段式

```text
短事务创建 check_run + runner operation/outbox
→ 事务外执行已批准检查
→ 短事务存不可变 report + event + 下一步意图
```

同一 checkRun 重投不重新启动可能仍在运行的进程。明确失败后如策略允许重试，创建显式 attempt_no+1，保留前次证据和重试原因；unknown 不自动重试。所有检查汇总由 policy evaluator 计算，不由 HTTP 提交一个 passed=true。

## 14. 最终审核与技术门槛

### 14.1 最终审核不是复用阶段审核结论

某阶段审核针对当时的 CandidateSet；最终审核针对组合后的完整 integrationVersion。二者可能不同，旧 ReviewReport 不可直接插进最终审核列表。

新增：

```python
def open_final_review(session, *, cycle_id, reviewer_assignment_ref): ...
def submit_final_review(session, *, trusted_identity, body): ...
def evaluate_integration_cycle(session, *, cycle_id) -> IntegrationEvaluation: ...
```

ReviewRequest 至少绑定 requestId、versionId、treeHash、selectionHash、contractHash、policyHash、cycleId、允许响应者及其 session/assignment、期限。

审核环境使用固定只读集成材料。支持真实只读边界时自动派发；只支持提示词“不要修改”时不能声称拥有受控只读能力，按 manual_assisted/blocked 记录。最终审核角色由已确认策略决定，不能没有创建 request 就当没有必需审核。

沿用 D10 已建立的受信票据机制，使用独立 audience `integration-review`，并绑定 requestId 和实例主体。普通用户 bearer 意见走用户验收接口；`X-Reviewer-Instance-Id` 不赋予 Agent 审核身份。

同响应引用、同内容幂等；同引用异内容冲突。旧 cycle/session/版本响应保存历史但不影响新结论。最终审核不得直接调用内部 commit_accept。

### 14.2 技术评估函数

```python
def evaluate_integration_facts(facts: IntegrationFacts) -> IntegrationEvaluation: ...
```

facts 由服务读取真实表和对象指纹，不由公开 HTTP 接收。至少检查：

1. selection 仍对应有效确认的计划与放行范围。
2. 集成构建无未解决冲突，输入和树哈希完整。
3. 所有 required check 均有与当前 cycle/version/tree/policy/environment/config 匹配的有效报告。
4. 所有必需 final reviewer 已合法响应并满足冲突策略。
5. 内容完整性未失效，所需授权没有被撤回到不能使用该成果的程度。
6. 不存在混入其他版本、其他环境或不同参数的通过报告。

输出 passed/failed/blocked/waiting，不用一个 all([]) 判定通过。必需检查为空的软件交付或必需审核角色缺 request，不能通过。非适用项需要来源于已确认策略的 not_applicable 解释，不由运行 Worker 自行删检查。

复用 EvidenceFingerprintRow 时，指纹必须包含 content/tree hash、contract hash、checkDefinition/config hash、输入版本和环境；集成事实还须绑定 version/cycle。不同候选/不同树的多个 passed 不能拼成当前整体通过。

### 14.3 修复、重跑与证据失效

- 内容/基线/输入选择改变：新 integrationVersion，新检查和审核。
- 内容不变，明确重试瞬态环境错误：新 check attempt，保留历史。
- 检查策略或环境改变：新 validation cycle，旧报告只在完整指纹匹配并有审计理由时复用；初版可保守地全部重跑。
- 单纯重新汇总未变证据：可新 manifestRevision，不能改原 manifest。
- 用户改计划/分配/门槛：使当前交付指针不可接受，回 D08/D11 的正式流程。

修复请求交给当前角色和授权范围；不能让最终审核实例直接修改集成目录。冲突解决后的新树也必须经过最终整体检查，不因为“只是修了合并冲突”省略测试。

## 15. 交付 manifest 应该如何生成

### 15.1 固定 manifest schema

建议主体：

```json
{
  "schemaVersion": "1",
  "runId": "run_example",
  "integrationVersion": "iv_example",
  "validationCycleId": "ic_example",
  "manifestRevision": 1,
  "planVersion": 2,
  "assignmentVersion": 2,
  "gatePolicyVersion": 1,
  "selectionHash": "<sha256>",
  "baselineHash": "<sha256>",
  "treeManifestHash": "<sha256>",
  "contractHash": "<sha256>",
  "integrationPolicyHash": "<sha256>",
  "environmentFingerprint": "<sha256>",
  "members": [],
  "checks": [],
  "reviews": [],
  "knownRisks": [],
  "technicalStatus": "blocked"
}
```

这里只展示形状，空 members/checks 的例子是 blocked，不能拿它当通过样例。

每个 member 包含 memberId、kind、required、safeRelativePath、object/hash、sourceCandidateRef、sourceReleaseRef、依赖成员、适用检查/审核引用、memberTechnicalStatus。最终代码树也有一个明确 member；不能只列几个说明文件就隐去源码树。

checks 包含 checkId/version、configHash、checkRunId、reportId/hash、outcome、环境和输入指纹；reviews 含 request/report、审核者受信身份引用、verdict、绑定指纹。风险区分 known_failure、unsupported、not_run、unknown_cost、manual_step，不能全塞一句“有少量限制”。

manifest 不存凭据、内部签名票据或完整宿主私密路径。公开视图与内部证据引用的读取权限分别校验。

### 15.2 哈希怎么计算

新增：

```python
def canonical_manifest_bytes(payload: DeliveryManifestPayload) -> bytes: ...
def compute_manifest_hash(payload: DeliveryManifestPayload) -> str: ...
def build_delivery_manifest(session, *, version_id, cycle_id) -> ManifestBuildIntent: ...
def publish_manifest(engine, store, *, intent_id) -> DeliveryManifestView: ...
```

规范规则：

- 使用明确 schemaVersion 和规范化 UTF-8 JSON，keys 排序、紧凑分隔、禁止 NaN/Infinity。
- 只对无序语义的集合按稳定 ID 排序；有业务顺序的合成输入不能排序丢掉原顺序。
- 时间统一 UTC，数值和 Decimal 序列化规则固定；尽量以结构化状态替代自由文本浮点估算。
- `manifestHash` 字段本身不加入待哈希主体，避免循环；生成时间放独立元数据，或固定一次后连同内容不可变。
- 风险、检查结果、成员列表等会影响用户决定的字段必须入哈希。隐藏这些字段会允许相同 hash 对应不同验收内容。

对象写入可以在事务外完成；采用 intent → 写内容寻址对象 → 短事务校验输入指纹/引用并发布的模式。事务失败留下的孤立对象以后按 GC 策略处理，不假装文件存储和数据库自动原子提交。

发布后给该版本与所有被引用内容加持久引用/保留保护，GC 不能删除待验收或已接受成果。下载时仍校验对象哈希；发现损坏记录失效事件，历史验收意见保留但不能继续声称可下载完整成果。

### 15.3 发布当前交付指针

锁顺序建议：Run → run_deliveries → 当前 version/cycle/manifest → 控制/决定子记录。与 D11 控制流程共享 Run 行锁，避免接受与取消/重规划并发。

发布时比较计划/交接/selection/cycle 仍是当前合法组合。成功后原子更新 current_version/current_manifest、提高 deliveryRevision、写 run.delivery_ready 或 integration.reviewable 等准确语义事件。

只有 technicalStatus=passed 的完整成果才令 Run.awaiting_acceptance。失败/阻塞版本可以发布为 reviewable 诊断材料供用户拒绝或查看，但不能用同一 delivery_ready 事件暗示已经技术通过。

原 `DeliveryReadyPayload` 的 artifact_count 至少为 1，实际空成果必须阻塞；不能为通过模型校验虚构一个文件。

### 15.4 不变版本和“当前”是两件事

GET 某个 manifestHash 返回该不可变内容，不随 current 指针改变，其 ETag 可使用 manifestHash。GET /runs/{id}/delivery 返回当前指针与 deliveryRevision，并给出用于写决定的强 ETag `"delivery:<revision>"`；不能把这两种 ETag 混用。

产生新版本、新检查轮次的重新发布、撤回或内容失效都要更新当前指针/修订并发版本。旧版本可下载/查历史，但旧验收请求不能对当前版本生效。

## 16. 用户验收：完整、拒绝、部分接受如何写

### 16.1 请求形状和前置条件

沿用主文档 `POST /api/v1/runs/{id}/acceptance`，写入必须有 Bearer、Idempotency-Key 和强 If-Match，例如 `"delivery:17"`。If-Match 绑定 deliveryRevision；请求体再明确绑定用户看到的 Run.statusVersion。

```json
{
  "integrationVersion": "iv_example",
  "manifestHash": "<sha256>",
  "manifestRevision": 3,
  "expectedStatusVersion": 28,
  "decision": "partial_accept",
  "acceptedMemberIds": ["member_docs"],
  "rejectedMemberIds": ["member_code"],
  "note": "先保留文档，代码需要按报告修复"
}
```

推荐 decision 固定为 accept/reject/partial_accept。完整 accept 由服务计算所有必需成员，不能允许客户端遗漏失败项却声称是 full accept；partial 必须给明确非空真子集。

请求体不接收 actorId、technicalPassed、checkReports、allowedCandidateIds；这些都由服务器和认证主体读取。

### 16.2 验收服务的方法

```python
def decide_acceptance(
    engine,
    *,
    principal: AuthenticatedPrincipal,
    run_id: str,
    expected_delivery_revision: int,
    idempotency_key: str,
    body: AcceptanceDecisionRequest,
) -> AcceptanceResult: ...
```

实现步骤：

1. 认证和资源权限校验，生成规范请求 hash（包含前置版本和决定范围）。
2. 在 Run 行锁内查询同主体/操作/幂等键。若原请求完全一致，返回原决定及 isCurrent 标记，不再次修改当前 Run；同键不同内容 409。
3. 锁 run_deliveries，核对 If-Match、currentVersion、manifestHash/revision 和 expectedStatusVersion。
4. 核对当前 Run 无冲突的 cancel/replan、新代次或未结束写入；验收对象仍属于当前确认范围。
5. 加载不可变 manifest 的安全主体与实际证据引用，核对完整性记录、当前技术结论和未决阻塞。
6. 按决定类型校验成员范围和依赖闭包。
7. 追加 AcceptanceDecision，更新用户验收投影，并提高 deliveryRevision 与相应 Run.statusVersion，使同一旧前置版本不能被第二个不同决定再次使用；只有满足完整完成条件才更新 Run.completed。
8. 同事务写 typed event 和必要 outbox。事件提交后 SSE 才可读取。

同键重放后当前版本已经变化时，返回历史决定不代表重新接受当前版本；响应必须显示 isCurrent=false，且不把新版本标接受。

### 16.3 三种决定分别怎么处理

**accept**：要求当前完整技术门槛 passed、所有必需成果有效、必需审核存在且通过，无需要用户另行处理的强制阻塞。成功后 acceptanceStatus=accepted；在没有冲突的活跃执行、计划变更和未处理原生写入时 Run.completed。

未决费用若策略允许作为已披露风险，不必伪造结算；若用户确认的预算/验收策略要求成本对账，unknown_cost 属于阻塞。验收不能修改 usage/settlement。

**reject**：可以对当前可审阅 manifest 记录拒绝，即使技术检查已经 passed。technicalStatus 保持原事实；acceptanceStatus=rejected，Run 转明确 blocked/waiting_rework 的现有可用映射，并保留用户理由。重开开发通过 D11/D10 定向返工，不自动直接写集成目录。

**partial_accept**：逐项检查 acceptedMemberIds 存在且没有重复、不与 rejected 重叠；选定项对应版本的适用检查/审核有效，依赖闭包全部在已满足范围内。必需共享整体检查失败时，不能接受依赖它的代码 member；真正独立的文档可以按自己的适用策略接受。

部分接受不把全局失败改 passed，不令 Run.completed；保存 accepted、rejected、未决定集合。Run 保持符合实际的 awaiting_acceptance/blocked 状态，用户决定投影为 partially_accepted。

后续新 manifest 不能按同名 memberId 自动继承旧接受。默认重新确认；如果要复用，必须证明内容、契约、适用检查、依赖和环境指纹完全相同，并让用户看到明确继承规则，初版可不支持。

### 16.4 并发与完整性边界

两个不同的决定请求争同一 deliveryRevision，只能一个成功改变当前投影；另一个返回冲突。决定历史追加保留，不用最后写覆盖前一条。

检查对象完整性可能有文件 I/O，不要把遍历整个树放进验收事务。可先生成受信完整性核对 receipt，绑定版本/对象/存储完整性修订，然后锁内校验 receipt 和引用版本未变化；对象存储必须内容寻址、受管写入和 GC 引用保护。若后续检测损坏，同一 Run 锁下撤回当前交付并发事件。

这不是声称数据库行锁能阻止操作系统管理员修改磁盘。平台能做到的是受管存储约束、哈希验证、失效传播和不复用过期证据；检测到坏内容后不能继续报告当前交付有效。

### 16.5 接受后也没有 push/deploy 意图

acceptance 事务不得创建 git.push、deploy、publish_site 等 outbox。若未来需要推送，另建带目标仓库/分支/commit 的用户授权与操作账本。当前只提供受控下载/导出，导出目录也由路径授权单独检查。

本批不做前端；CLI JSON 输出与 API 共用同一契约。终端显示明确区分“已创建构建”“检查中”“技术通过”“等待用户验收”“部分接受”和“已完成”。

建议按实际需要注册：

| intent | 处理器 | 成功/失败的领域证据 |
| --- | --- | --- |
| integration.build | process_integration_build | integration_build + 固定 IntegrationVersion 或冲突/unknown |

所有新 payload 都有 operationId/taskVersion，dispatcher 路由有契约测试。Worker 结果写事件和 D11 WakeSignal（需要时），不在 HTTP 中靠内存回调接下一步。SSE 不占 Worker/Run lease。

integration.* 由受信控制 worker 消费，只有检查执行环境拿到最小必要数据。普通 queue worker 不获得 app 任意写权限、API bearer 或内部签名密钥。并发从低值开始：单个集成构建/整体测试优先保证内存和恢复正确性。

## 19. 必须覆盖的测试矩阵

| 场景 | 如何制造 | 必须成立 |
| --- | --- | --- |
| 快照并发 | 一个连接更改阶段/指针并提交，另一个读取快照 | 响应来自同一视图，latestSequence 对应同一视图 |
| 未提交事件 | 事务中写 Event 暂不提交 | SSE 看不见，回滚也不发送 |
| 事件回滚/序号竞争 | 多写入者并发并随机回滚 | 已提交序号唯一、连续可补读 |
| 快照与连接间有更新 | 取 N 后提交 N+1 再连 SSE | N+1 被补读，不丢 |
| header ID 与数字游标 | 同时给不一致值/跨 Run ID | 409，不泄露其他 Run |
| 帧解析 | 每个 UTF-8 字节边界切块，多行 data/注释 | 客户端正确重组，不按 chunk 当帧 |
| payload 注入 | 文本含换行、id: 和恶意脚本 | JSON 数据保持数据，不注入字段/执行脚本 |
| 重复/乱序 | 重投相同 event，先给大序号 | 不回退；缺口补读/快照，不跳过 |
| 窗口推进 | N 快照后 floor>N | resync_required，不假装连续 |
| 内部事件投影 | 含敏感路径/内部 ticket 的事件 | 无敏感信息透传，序号仍可解释 |
| 凭据撤销 | 已连接后撤销/过期 | 在规定检查间隔后停止内容并清理资源 |
| 慢客户端 | 实际 TCP 连接停止读取 | 发送超时/连接上限工作，内存有界，DB 不被长期占用 |
| 流取消 | Ctrl+C/连接中断/服务 drain | finally 释放 slot/连接，不修改业务成功状态 |
| 产品计数 | 同产品多 profile，能力过期，实例 unknown | 三类数量与分类准确 |
| 未放行输入 | 传任意 snapshotId/额外源文件 | selection 拒绝，不扩大 ReleaseRecord 范围 |
| 基线未提交修改 | baseline 带 managedDirtySnapshot | 集成保留准确已确认基线，不退回干净 HEAD |
| 并行文件变化 | A 改 x，B 保持 x 基线且改 y | x/y 合并正确，不被全树覆盖 |
| 文件冲突 | 同路径异内容、写删、大小写碰撞 | conflicted，保留来源，不静默选一方 |
| 构建崩溃 | Git/解包完成后退出，DB 未完成 | 核对原目录/结果或 unknown，不重复新建 |
| 非确定归档 | 相同树归档元数据不同 | treeHash 不误变；blobHash 单独记录 |
| 缺检查能力 | 只存在 path_exists 或容器 unsupported | 整体测试 blocked，不能宣称已执行 |
| 空/跳过测试 | 收集 0、全部 skip 或缺必需场景 | 按策略 blocked/failed，不全局 passed |
| 测试篡改输入 | 检查程序试图写源码 | 边界阻止或完整性失败，报告不通过 |
| 超时子进程 | 父进程退出但子进程仍活动 | unknown/needs_reconciliation，不复用可写环境 |
| 报告伪造 | 只有 Agent 的 passed.json/JUnit，无可信执行 | 拒绝成为权威报告 |
| 版本证据混用 | 把 iv1 报告放 iv2 或改参数/环境 | evidence_mismatch，不通过 |
| 最终审核遗漏 | 策略要求角色但没 request | waiting/blocked，不空集合通过 |
| 旧审核重放 | 旧 cycle/session 响应、同 ID 异正文 | 不改新结论，冲突可审计 |
| manifest 哈希 | 改成员/风险/检查，或变序无序集合 | 语义变动 hash 变；无序等价规范稳定 |
| 旧验收 | iv1 页面未刷新而当前变 iv2 | 409，不接受 iv2 |
| 双决定竞争 | accept 与 reject 同 revision 并发 | 一个改变当前决定，另一个冲突 |
| 幂等重放 | 同 key 重发原决定，当前版本已变化 | 返回历史 isCurrent=false，不重写当前 Run |
| 部分接受依赖 | 接受依赖失败共享检查的 member | 拒绝；独立通过项可按范围接受 |
| 验收与取消 | cancel/replan 与 accept 并发 | 由同 Run 锁/版本串行确定，不出现已取消又静默完成 |
| 接受与发布边界 | full accept | 无 git.push/deploy 等未经授权 intent |
| GC 与内容损坏 | 待验收对象清理竞争/对象坏哈希 | 引用保护或失效事件，不能继续有效交付 |

### 19.1 最小纵向用例

先用真实 PostgreSQL、真实临时 Git 仓库和受控原生替身实现：

1. D11 给出 A→B 的合法 IntegrationHandoff。
2. A/B 的固定输入在各自 D10 ReleaseRecord 中放行。
3. 客户端取一致快照，并从 latestSequence 开始 SSE。
4. 持久构建 iv1，执行已注册真实整体检查，制造一个组合缺陷。
5. iv1 failed，客户端通过补读看到它；用户完整 accept 被拒。
6. 通过正式定向返工得到新候选和 selection，构建 iv2。
7. iv2 的整体检查和最终审核通过，生成 manifest M2。
8. 使用 M1/iv1 的验收请求返回冲突。
9. 使用当前 deliveryRevision、M2、iv2 接受，Run.completed 与事件同事务。
10. 断线重连后通过补读得到同一完成事实，重复请求不产生任何新原生动作。

替身只能证明平台机制。R15 完整验收还要求至少一次两种已验证外部 Agent 产品的真实流程；产品能力仍 unknown/unsupported 时如实列为待验收，不能用两个 mock 代替。

## 20. 从哪里开始写，怎样避免一上来写成大工程

第一步做 D12-01～D12-03：定义快照与交付契约，建立当前交付/历史记录的版本语义，写同一事务的 SnapshotQueryService。

第二步只接最小 SSE：从快照 afterSequence 补读，支持 eventId 重连、心跳、断线、过期重同步。暂时不用 token 流、Redis、广播总线或复杂前端。

第三步把一份合法固定 selection 构建成独立集成版本，先测基线差量与冲突，再接真实整体检查和最终审核。

第四步做 manifest 与验收：先完整接受/拒绝，再做有依赖约束的部分接受。只有当前版本技术通过并被完整接受，才推进 completed。

这四步分别有可演示结果，每一步都沿用既有授权/队列/恢复和事件事务。不要先堆大量列表路由，再最后才发现“用户接受的到底是哪一个版本”没有固定。

## 21. 本批交付检查清单

- 快照来自同一一致性视图，latestSequence 有明确含义。
- 三类 Agent 数量分开，库存 revision 与 Run 事件 scope 不混淆。
- SSE 先落库后发送，Last-Event-ID 与现有 eventId 契约一致。
- 心跳/控制帧/token/logs 不伪造业务成功，也不占业务 sequence。
- 保留窗口、缺口、未知类型、慢客户端、撤销和断开行为有实现和证据。
- 集成只消费已放行的固定范围，保存完整代码树/单文件的准确授权语义。
- D07 构建与 D05 真实检查接成可恢复、不可盲重放的正式链路。
- 所有必需整体检查与最终审核绑定同一版本/树/参数/策略/环境。
- manifest 不可变，当前交付指针有版本，旧确认不能接受新版本。
- 用户决定和技术事实分开，部分接受不掩盖失败，全量 completed 有明确条件。
- API/CLI/schema、迁移与角色说明、自动化负例、真实两产品证据齐备。
- 文档和验收报告明确区分“设计”“平台自动化通过”“真实产品通过”。
