## 2 代码发现

### F01 [P1] Runner接受客户端任意根目录、虚构归属和代次，未实施票据授权边界

位置：runner/service.py:68～112、155～188；api/runner.py的issue/execute；contracts/runner.py:32～49。

issue只确认workspaceRoot是已存在目录，然后将用户传入workspaceId/nodeId/attemptId/generation/scope抄到账本。execute不查受信工作区登记、当前运行代次、有效attempt/lease或节点归属；scope没有限制params中的实际路径，requireEffectiveApproval由客户端选择且默认false，指定approval时也没有把其动作摘要/范围和ticket对账。

通过真实PostgreSQL临时runner_operations表和生产RunnerService复现：workspaceId未登记、nodeId不是local、attemptId不存在、generation=999、scope指向其他目录，仍可issue并read_snippet成功，读取本轮临时目录中的合成文本。没有授权该临时目录的Project/DirectoryGrant。API直接以普通用户Bearer调用该服务，并非受信服务签发、Runner独立验签的操作票据。

修复：由可信控制服务根据授权登记解析根目录和范围，客户端只能指定受控ID；短期票据绑定准确操作、节点、工作区、attempt/generation/有效lease并在线核对；审批要求来自策略而非调用者自选。按方案建立独立Runner身份/执行边界，平台API不承担宿主文件执行。容器能力现始终blocked，不能计BE-07/21完整通过。

### F02 [P1] Runner文件副作用与状态同事务，异常回滚后可重复执行

位置：runner/service.py:177～202；api/runner.py execute的UoW。

running仅flush而未提交便执行文件操作。异常时设置needs_reconciliation又抛RunnerError，上层UoW整体rollback，连风险状态也丢失，原票据重新呈issued。同一operation没有原子条件领取，两个并发执行还可同时通过issued检查。

真实PG临时表/savepoint复现：先保存issued票据；受控profile先写合成文件再抛异常；按调用方回滚后，文件仍存在而账本回到issued。再次execute同ID会再次执行，副作用计数2并返回succeeded。

修复：短事务原子领取并持久登记执行意图；Runner本地账本与真实进程/容器ID记录先行，副作用在事务外；结果用独立短事务回写，未知状态持久保留。重复/并发请求不得重新执行，增加真实数据库和中断窗口测试。process_ref='host:'+operationId不能作为真实进程证据。

### F03 [P1] 停止证明可凭标记文件制造，并跨工作区复用；Git冻结无停止检查

位置：runner/profiles.py:228～239、runner/service.py:217～235、artifacts/service.py:65～91及382～409、git/service.py:197～221。

close_task直接写stopped=true；record_stop_evidence没有检查操作状态或相关子执行，running操作也能生成该标记。ArtifactService只核对任意终态RunnerOperation的generation/可选attempt，不核对workspace/root/node/实际可写范围，不要求其执行过可信停止检查或匹配账本保存的停止结果；只要用户提供文件的哈希一致即可。

真实PG临时表复现：running operation调用record_stop_evidence仍返回stopped=true；随后用一个属于另一个workspace的read_snippet成功操作，提交不同workspace/root、虚构project、另一个文件写有{"stopped":false}的证据，freeze_candidate仍成功frozen。source='runner'的类型常量不是来源证明。

D07 stopOperationId是可选字段，freeze_snapshot只保存该值，不查询或核验；真实Git定向测试不提供stopOperationId，仍返回快照。snapshot.py:83～90先扫描manifest后再次扫描tar，来源仍可变时二者也可能不对应同一内容版本。

修复：可信Runner核查真实进程、可写子执行和权限静止状态，绑定workspace/attempt/generation/范围/证据哈希及来源；拒绝未知和无关操作。D06/D07统一消费可信停止记录，缺失时blocked。固定快照的manifest应针对实际归档的相同字节计算，不能靠两次可变目录扫描承诺一致。

### F04 [P1] Git worktree checkout仍会运行仓库自带filter命令

位置：git/safe.py:91～109，git/service.py worktree add调用。

run_git禁用hooks、diff.external等，但保留本地仓库配置和.gitattributes中的smudge/process过滤器。shell=False只约束Python启动Git，不约束Git自身调用的外部程序。当前Git工作还在API进程上下文运行。

仅使用临时仓库复现：审核者登记一个filter.review.smudge合成Python脚本，只写临时标记文件；提交.gitattributes对应文件后调用当前run_git(worktree add --detach ... HEAD)，exit=0且合成脚本在宿主执行。没有用户项目脚本、网络或真实秘密参与。

修复：将不可信checkout/配置驱动操作放到受控执行边界，或使用不会执行仓库配置扩展的可信内容提取/工作区准备策略，明确过滤器/子模块/LFS限制；不能只加hooksPath便宣布无外部执行。测试clean/smudge/process、fsmonitor、工作树配置和子模块等真实行为。无法满足时拒绝该仓库/策略，不能在宿主默认执行。

### F05 [P1] 集成使用整树覆盖，删除丢失，独立改动出现假冲突

位置：git/service.py:263～303。

实现并未计算baseline→candidate差异，而是把每个候选整棵文件树依次覆盖到基线工作区；归档中缺失的删除项不会应用。候选未修改的基线文件也会被当成要覆盖的内容，因此把前一候选的合法修改视为冲突。

真实Git+现有测试harness（Session为测试替身）复现：

| 场景 | 实际结果 |
| --- | --- |
| 仅一个候选删除shared.txt，随后集成 | status=ready，shared.txt又存在，删除被静默丢失 |
| 候选A只改README，候选B只新增only-B.txt | status=conflicted，README被误报冲突 |

修复：依据同一基线计算带增删改/重命名等语义的patch或真实三方合并，区分未改基线与候选修改，保留所选快照ID/哈希及合并来源；集成修复产生新版本。补删除、rename、独立文件、相同文件不冲突改动、真正冲突、mode和受支持symlink用例。不能用两个候选同改一个文件的唯一测试代替正确集成。

### F06 [P1] 产物GC未计入Git快照引用，会删除仍可恢复的对象

位置：artifacts/service.py:338～372、433～439；git/service.py的_upsert_content。

GC的引用集合只扫描ArtifactCandidateRow与ArtifactPublicationRow。D07的GitDirtySnapshotRow、GitWorkspaceSnapshotRow和GitIntegrationRow也使用同一个ArtifactStore/ContentObjectRow，但未进入引用集合，且D07新建内容元数据未设置保护期。正常GC标记并经过宽限后可删除仍被上述记录引用的恢复对象。

真实PG临时0011/0012表复现：保留一个GitWorkspaceSnapshotRow指向对象、元数据已过宽限，执行当前ArtifactService.gc，结果deleted包含该hash，Git snapshot行仍在，但store.has=false。只删除本轮临时store对象，数据库整体回滚。

修复：建立统一引用/pin登记，涵盖候选、Git快照/集成、报告、checkpoint、模板、备份和运行保留；并发新增引用与GC删除需有共同原子协议。增加D06/D07联动GC回归，不能仅测两个artifact表。dryRun也应说明是否只读，当前首次标记仍修改元数据。

### F07 [P1] 任意弱验证通过就覆盖候选失败并允许发布

位置：artifacts/service.py:141～198、248～264；freeze的contractHash生成不包含必需criteria/validator定义。

调用方选择一个validatorId执行，任何passed都把候选状态设verified；publish只需要存在至少一份passed报告，不核对注册交付契约中的完整必需检查、失败/未运行项或validator版本集合。首次冻结也接受任意contractId，没有加载真实契约及必需规则。

当前生产服务+临时文件/测试Session复现：同一个二进制文本候选先经utf8_text得到failed，再经sha256_presence得到passed，随后可published。另一个包含语法错误代码的候选，仅hash存在验证也可verified/published。stage_released=false仍是正确的，但不能用未来D10门禁代替当前“已技术验证”状态的真实性。

修复：绑定真实契约哈希/版本及必需验证集合、环境和每项结果，只有必需项全部具有匹配的可信报告才聚合verified；一个可选或弱检查不得覆盖失败。文件存在/UTF-8有效不是完整技术验收。补先失败后弱检查、缺项、not_run、旧validator/环境报告及新候选失效测试。

### F08 [P2] force清理绕过活跃集成引用，未核对仍在运行的attempt

位置：git/service.py:350～373；contracts/git_workspaces.py中force说明。

cleanup仅在存在pending/merging/conflicted集成且force=false时拒绝；force=true直接调用强制移除，没有核对相关Agent/attempt/子进程或停止证明。即使force=false，没有集成记录的active工作区也可被删除。现有test_cleanup_refuses_user_root_and_active_refs显式断言force可以删掉仍被conflicted集成引用的工作区，与契约“force仍拒绝active refs/processes”和方案“清理前确认没有相关执行与有效引用”冲突。

修复：force只能影响已安全停止后可丢弃内容的策略，不能绕过归属、执行和有效引用门槛；强制路径仍应保留明确停止核查/人工处置结果。操作目标需验证属于平台wt_root且身份未被替换，不能只比较是否等于用户源目录。新增活跃attempt、未知子进程、引用与目录替换用例。
