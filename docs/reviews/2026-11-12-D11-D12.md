## 2. 必须修复的发现

### F01 [P1] Driver 中断后不会按多数真实结果恢复，还会吞掉唤醒

位置：`src/agentforge/driver/waits.py:102–117,242–258`；`src/agentforge/driver/service.py:241–274`；`src/agentforge/driver/nodes.py:277–295`。

workspace_ready、native_approval、stage_review、user_gate_decision、stop_verification、recovery_evidence、capacity 的 predicate 仍指向 `_pred_always_false`；driver_yield 自己也固定 false。session_ready 虽有实现，但 `register_wait_action` 仅放 stageId/workPackageId，没有 predicate 所要求的 instanceId。

已有 interrupt 时 `drive_once` 只根据 `recheck_open_wait` 决定是否 resume。条件为 false 就直接返回，并将本次 claimed signals 标 completed。实际审核/停止/恢复结果即使已入库也无法让该片段 refresh；控制请求同样可能被旧等待挡住。还有 driver_yield 没有建立可满足的内部屏障/正式继续协议。

证据：直接登记 stage_review wait 后调用真实 WaitService，结果始终 waiting；其他占位 reason 的源码逻辑相同。信号完成分支在等待复核之前没有重新读取这些领域结果。

修复：为每个 reason 实现版本化事实 predicate，补齐 instance/attempt/cycle/case 等 scope；控制信号可安全取消/替换旧等待并重新决策；等待满足/重新观察后才完成覆盖到的 signals。内部 yield 必须有持久继续信号并且可解析，不能永远 false。加真实 PostgreSQL + checkpoint 的“interrupt → 外部结果/取消 → 新进程 drive”测试。

### F02 [P1] 官方 CLI 启动的 worker 不消费 agentforge-driver 队列

位置：`src/agentforge/cli/main.py:825–873`；`src/agentforge/queue/tasks.py:132–170`；`src/agentforge/queue/dispatcher.py:125–134`。

driver.wake 被投递到 `agentforge-driver`，driver_step 也注册在该队列；但 `queue work` 只消费默认队列，`queue work --control` 只消费 `agentforge-control`，没有 driver 队列的启动选项。现有正常启动方式无法实际执行已经排队的 Driver 任务。

修复：提供明确的受信 driver worker 入口，或让受信控制进程显式消费 control+driver，并做角色/迁移/能力校验及协调容量限制。补一次真实 defer → worker → DriverResult 的集成测试，不能只断言 task 注册。

### F03 [P1] Driver 的计划字段映射和初始化顺序使正式派发无法正常到达

位置：`src/agentforge/driver/snapshots.py:176–207`；`src/agentforge/driver/planner.py:104–115`；`src/agentforge/driver/dispatch.py:83–98`。

PlanWorkPackageSpec 的真实字段为 ownerRoleId，SnapshotReader 却只读 roleId/role_id，所以 role_id=None。它将逻辑 stageId（例如 stg_impl）直接作为运行阶段 ID；真实 StageRow 是 run:p1:stg_impl。DispatchService 会优先使用 planner 传入的 stage_id，导致查错 stage 或准入拒绝。

此外，没有实例时 planner 先选 ensure_instances，而 D09 prepare 明确要求已经有真实工作区；ensure_workspaces 反而只在“已有实例但 workspace_id 为空”时触发。正常从已确认计划起步会循环尝试失败的实例准备，不能先建立工作区。

证据：用当前正式 PlanSpec 夹具运行真实 SnapshotReader，得到 role_id=None、stage_id=stg_impl，而实际阶段为 run:p1:stg_impl；无实例/无工作区快照的 next_action 为 ensure_instances。

修复：使用 PlanSpec 的类型化字段，不手工猜字典别名；集中使用物理 Stage ID 映射；Snapshot 显式包含已准备工作区，按 workspace→instance→session→dispatch 排序。测试必须从真实批准计划启动，不只手工构造已经满足先决条件的 WorkPackageSnap。

### F04 [P1] 提交和返工节点只有外观，正式图没有完整推进路径

位置：`src/agentforge/driver/planner.py:10–189`；`src/agentforge/driver/nodes.py:459–475,566–584`；`src/agentforge/driver/graph.py:17,47,65`。

planner 没有产生 accept_submissions 的路径，Snapshot 也没有待桥接的正式提交消息；节点又要求 action_detail 为 message:msg...，否则直接无动作。内部 agent-messages 入口只保存消息，没有调用 SubmissionBridge 的正式桥接。结果是结构化提交已存储也不必然到达 StageService.submit。

prepare_rework 仍写着 deferred，只建立 recovery_evidence wait，不执行“停止/关闭旧会话 → 新工作区 → accept_rework → 新 attempt”的约定流程。

修复：把未处理受信 submission 引用放进 Snapshot/专门桥接任务，设置稳定消费键，确实调用 SubmissionBridge；实现返工 coordinator，不能以永久等待代替开发完成。补正式提交到真实 D10 放行、至少一次定向返工的纵向用例。

### F05 [P1] 恢复决定写 applied，但没有执行对应恢复动作；报告接口还会直接 NameError

位置：`src/agentforge/recovery/service.py:264–321,448–492`；`src/agentforge/driver/control.py:285–326`；`src/agentforge/api/collaboration.py:183–209`。

apply_decision 追加决定并把 case 标 applied 后就返回，没有按 resume_existing/handoff_new_session/continue_stage_processing 分派实际协调操作，也没有推进原 Run 控制 operation。prepare_resume_operation、handoff 构造器和 apply_verified_resume 没有接成该公共流程。

另一个内部入口 `apply_verified_resume` 允许 recovery_case_id=None，只要没有它枚举到的 unknown 就直接改 running；即使传 case，对 applied case 的错误 action 也可能放过。该入口的名字不能代替证据校验。

RecoveryService.get_report 使用 RecoveryReport，但模块没有导入它；当前公开报告路径实际抛 NameError，而不是只存在一个注解静态错误。

证据：真实服务调用 get_report 已复现 NameError；隔离 PostgreSQL 中 paused Run 不传任何 recovery case 调用 apply_verified_resume，返回 running。

修复：每类决定形成可查询、可恢复的实际应用 operation；安全完成后才 applied/恢复运行。case 强制绑定当前上下文和必需观察，错误 action/无 case 拒绝。导入报告契约并测真实 API；不能仅断言决定行插入成功。

### F06 [P1] D12 构建/检查 outbox 无消费者，payload 也不满足 dispatcher

位置：`src/agentforge/integration/coordinator.py:184–190`；`src/agentforge/integration/check_worker.py:182–189`；`src/agentforge/queue/dispatcher.py:114–188`；`src/agentforge/queue/tasks.py:63–170`。

写入的 intent 为 integration_build / integration_check，但 dispatcher 和 Blueprint 都没有对应链路；payload 又缺统一要求的 operationId。原生队列执行不到实际 process_check_run。

HTTP 构建入口在接受意图之后立即同步调用 process_integration_build，只遮住了部分构建问题，并不能修好 outbox 重投/进程崩溃后的正式执行。检查接口只开 cycle，不会同步执行测试，之后没有可达 worker。

证据：对实际 payload 调用真实 `_enqueue` 抛 missing operationId；补 operationId 后仍抛 unsupported intent_type。

修复：统一 intent/payload/taskVersion，成对实现 dispatcher 与任务消费者，HTTP 只返回持久接受结果。所有结果落账后接入下一步检查/评估/manifest 调度，做真实队列重启验收。

### F07 [P1] 软件集成使用空基线，完整代码树不支持，成功版本也没有可恢复的树对象

位置：`src/agentforge/integration/coordinator.py:202–235`；`src/agentforge/integration/builder.py:271–350`。

`_baseline_manifest_from_selection` 无条件返回 {}，没有加载固定 Git 基线/managed dirty snapshot。候选只转为一个文件；带 treeHash 的完整代码树明确 blocked。实际版本可能只是部分交付文件集合，而丢失所有未改动的源代码和依赖。

builder 最后把树/对象清单做摘要，作为 content_hash 返回，但没有把归档或树 manifest 写入 ArtifactStore。随后 IntegrationVersion 和交付 manifest 用这些哈希当内容身份，脱离可变工作区后没有对应存储对象可恢复/下载。

证据：空基线函数返回 {}；真实临时文件 materialize 返回 succeeded，但 store.has(result.content_hash) 和 store.has(result.tree_manifest_hash) 均为 False。

修复：加载准确、可读的基线树与批准差量，支持本批软件源码范围契约，保存确定性树清单/归档并建立 GC 引用；区别树哈希和实际 blob 哈希。完整树仍 unsupported 时应明确阻塞软件交付，不能称 R15 已完成。

### F08 [P1] unknown/running 操作允许重新领取，可能重复执行或并发清理同一工作区

位置：`src/agentforge/integration/check_worker.py:219–235,271–284`；`src/agentforge/integration/coordinator.py:251–255`；`src/agentforge/integration/builder.py:305–318`。

检查 Worker 允许 status=unknown 重新进入执行，而调用外部检查前已经提交 unknown。崩溃在进程启动后/报告保存前，同一任务重投会再启动检查进程。构建也允许 running/unknown/needs_reconciliation 再做 materialize，且 materializer 会清理已有工作区；重复任务可并发覆盖/删除正在用的内容。

没有足够的派发 claim token/CAS 与外部结果对账来区分“尚未开始”和“已可能启动”。

证据：隔离 PostgreSQL 中 executor 记录已派发后抛 SystemExit，两次 process_check_run 对同一 checkRun 共调用执行器 2 次。

修复：只让未派发状态转换为 committed dispatch intent；unknown/running 进入观察/对账，不原样重发。回执用 claim/binding 条件更新；构建目录用受控操作锁和实际结果核对。增加两 Worker 并发及派发后崩溃测试。

### F09 [P1] 整体测试未装载集成源码，且输入哈希是常量回填

位置：`src/agentforge/integration/check_worker.py:253–267,362–403`；`src/agentforge/integration/checks.py:154–166`。

process_check_run 仅 mkdir `_checks/<versionId>`，不从该 IntegrationVersion 的固定对象恢复文件，也不使用成功构建目录。默认测试在空目录执行；旧/人为留在该路径的文件又可能被误认为集成内容。

_host_execute 把 tree_hash_before 和 tree_hash_after 都直接赋预期 tree_hash，完全没有扫描或验证实际输入是否相同；requireContainer 强制 false，直接选择宿主执行，没有经过 D05 票据/相应宿主授权和受限环境判定。默认 communicate 收集无限 stdout/stderr，也未可信管理整个子进程树。

证据：隔离 PostgreSQL 捕获真实 approved request，cwd 中实际文件数量为 0。即使今后加源码复制，当前哈希回填仍不能证明测试输入未被更改。

修复：从固定对象恢复并验证输入，在受信执行环境中限制读写/子进程，输出单独 scratch；执行前后实际核对或使用真实只读输入证据。工具与环境固定并按权限执行；不支持隔离时如实 blocked/显式宿主模式，不自动 fallback。日志流式限量。

### F10 [P1] 检查策略没有绑定用户确认内容，非默认配置保存后会丢失

位置：`src/agentforge/api/integrations.py:188–207`；`src/agentforge/integration/check_worker.py:94–114,241–252`；`src/agentforge/integration/checks.py:335–378`。

公开 validation-cycles 接口无论 policyRef 传什么，都硬编码 tests/ 下的默认 pytest 检查；没有解析已确认策略、必需审核角色或相应配置。compile 默认给宿主能力与 Python 能力，也没有验证真实环境指纹。

cycle.required_checks 只保存 checkId/version/required/configHash，没有 config；执行时又用缺失 config 的 {} 重算。minimumCollectedTests、路径、marker、时限等非默认配置都无法按批准内容往返。

证据：隔离 PostgreSQL 可使用任意未确认 policyRef 开 cycle；minimumCollectedTests=3 开立成功，process_check_run 随后报 check_evidence_mismatch。

修复：加载不可变已确认策略、完整规范 config、review roles 与真实工具环境指纹；请求只选择策略引用，不能静默替换。报告指纹包含配置和版本，并在组装事实时再次核查。

### F11 [P1] 已取消/取消中的 Run 可被最终验收改成 completed

完成状态防护检查了拼写 `cancelled`，而真实枚举/数据库使用 `canceled`，且没有阻止 cancel_requested、pause_requested、重规划/活跃执行。只要请求使用当前 statusVersion/deliveryRevision，服务可用旧 manifest 的 technical_status=passed 直接完成 Run。

### F12 [P1] 重放旧 manifest 会回退当前版本，且不提高 deliveryRevision

### F14 [P1] 规范批准计划会令 D12 快照直接 500

### F15 [P2] 暂停/取消请求的同键重放会被自身状态变更拒绝

request_action 在查幂等记录前检查 expectedStatusVersion；第一次 pause/cancel 已提高 statusVersion，网络超时后重发同一个原请求会先报 status_version_conflict，无法取回已接受的 operation。

### F16 [P2] SSE 公开事件采用敏感键黑名单，不是类型字段白名单

位置：`src/agentforge/streaming/projector.py:26–72,134–151`。

KNOWN_TYPES 只限制事件类型，payload 则递归保留不包含关键字的任意键。自由文本 detail/note 里的凭据、workspaceRoot/sourceRoot/其他私密路径不会被阻止；不能把 `_scrub` 的键匹配当作公开字段白名单。

证据：对真实 project_public_event 输入包含 synthetic 的 detail='Bearer secret-in-free-text'、workspaceRoot='C:/private/project'，两者原样输出。这里使用的是测试字符串，没有读取/输出真实密钥。

修复：按每种事件定义公开 payload schema 和字段映射，不透传内部字典；日志/正文用受权 ID 读取；对于内部敏感事件保留安全 invalidation 占位维持序号连续。自由文本若可能含秘密要在来源和输出层明确处理，不能仅过滤键名。

## 3. 其他需要收口的风险

- `driver/service.py:276` 将 checkpoint/resume 探测的所有异常记录后“从初始输入调用”；遇到不兼容状态、数据库或序列化异常不应自动作为全新流程继续。正式节点仍靠领域幂等兜底，但应把不兼容 checkpoint 显式 blocked/recovery。
- `driver/service.py:287` 没有显式 sync durability；需验证与 fenced checkpointer 的保存/释放租约次序及所有异常关闭路径。
- `recovery/probe.py` 的工作区检查会使用 SQLAlchemy Session 执行文件/Git 核查；与宣称的完全事务外 probe 不一致。恢复范围也没有完整覆盖审批回传、候选对象完整性、预算未决账本。
- `driver/snapshots.py` 查询全部 Run stages/releases，没有完整过滤当前计划/分配；released_work_packages 汇总后可能混入旧计划同名工作包。prepare_handoff、selection 和最终验收均需端到端重新绑定，不能只靠名称集合。
- `integration/builds` 的版本号由 max+1 取得，完成阶段未按 Run 锁串行分配；并发构建存在版本号竞争及过期结果替换当前指针的风险。
- `integration/reviews.py` 将 content_integrity_ok 简化为报告 treeHash 等于预期，没有读取实际对象；build_conflict_free 也仅凭 hash 非空。不能据此声称已核验存储内容。
- `streaming/service.py::read_bounded_batch` 仍用默认隔离级别，不保证 replay window 与事件读取来自相同快照；清理并发时至少会产生不必要的 gap/resync。初次 SSE async 路由仍直接同步查库，长期连接的网络发送超时也没有实际实现。
- `get_or_create_delivery` / replay_window 的部分 GET/read 路径会插入数据，存在首读并发和只读职责不清；需要在 Run 初始化/正式领域事务创建，或使用并发安全条件写。
- 最终审核开立只保存请求行，缺少完整的只读上下文/派发/短期票据交付链；真实产品只读能力不能靠提示词替代。
- OpenAPI 与源码不同、125 个类型错误和 45 个 lint 问题需要按门槛修复；其中 undefined RecoveryReport、required 字段等已有实际运行错误，不能全部视为可延后的风格清理。

这些补充风险本轮有源码依据，未对每项都做独立并发/真实产品破坏性验证；修复时应分别补证据，不能将“未复现”当作“已通过”。

## 4. 为什么现有测试没有挡住

1. 很多单测直接手工构造 CollaborationSnapshot、IntegrationFacts、passed manifest 或 MagicMock，绕过正式 PlanSpec 字段、数据库完整约束和从源码树到检查的真实路径。
2. D12 integration_pipeline 测试自身注明是 stub/platform 层，主要调用纯评估/哈希函数，不是“handoff → 真实构建 → 队列检查 → 最终审核 → 用户接受”的纵向执行。
3. fault_matrix 的映射字典和条目数量测试能说明覆盖计划，不证明其对应故障已通过正式入口执行。
4. 51 个 skipped 涵盖未全局配置 PostgreSQL 的测试及主机符号链接条件；它们不是通过。本轮没有把指向现有业务库的 suite 直接强行执行，更没有为了跑测试自动迁移该库。
5. 构建、检查、决定函数分别单测通过，并不能证明相互之间的 source bindings、队列路由、版本和恢复语义兼容。
